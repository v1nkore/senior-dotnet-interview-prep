001В чём разница между value type и reference type? Где они хранятся в памяти?▶

Value type (struct, enum, primitives) хранит само значение; reference type (class, string, array, delegate) хранит ссылку на объект в куче.

Расположение зависит не от типа, а от контекста: локальные value-переменные обычно живут на стеке, но value-поле внутри класса лежит в куче вместе с объектом; захваченные замыканием или async переменные «уезжают» в кучу. Reference-объект всегда в managed heap, а сама ссылка — там, где объявлена.

Ключевые следствия: value копируются по значению (присваивание = копия), reference — по ссылке (две переменные на один объект). Сравнение: value — по содержимому (если переопределён Equals), reference по умолчанию — по ссылке.

002Что такое boxing/unboxing и чем он опасен для производительности?▶

Boxing — упаковка value type в объект на куче (object o = 42;), unboxing — обратное извлечение с проверкой типа. Каждый boxing — это аллокация в куче + копирование, что создаёт нагрузку на GC.

Опасность в горячих путях: боксинг в цикле, при работе с не-generic коллекциями (ArrayList), при передаче struct в object/интерфейс, в string.Format/конкатенации, при вызове Equals(object). Лечится дженериками (List<int>), Span<T>, перегрузками без object и реализацией IEquatable<T>.

003Как устроен сборщик мусора (GC) в .NET? Что такое поколения (generations)?▶

GC — поколенческий, mark-and-sweep с компактификацией. Поколения: Gen0 (новые мелкие объекты, чистится часто и быстро), Gen1 (буфер между 0 и 2), Gen2 (долгоживущие, полная сборка дорогая). Гипотеза поколений: большинство объектов умирает молодыми.

GC находит «корни» (стек, статика, регистры), помечает достижимые объекты, остальное освобождает и уплотняет кучу. Есть режимы: Workstation/Server GC (server — несколько heap'ов и потоков, для бэкенда обычно лучше) и concurrent/background GC для снижения пауз. LOH собирается вместе с Gen2.

004Что такое Large Object Heap (LOH) и какие с ним связаны проблемы?▶

Объекты ≥ 85 000 байт (например, большие массивы/буферы) попадают в LOH. Исторически LOH не уплотнялся → фрагментация: память занята, но крупный блок выделить негде. Сборка LOH идёт вместе с Gen2, то есть редко и дорого.

Решения: переиспользовать буферы через ArrayPool<T>/MemoryPool<T>, избегать частых крупных аллокаций, при необходимости вызвать компактификацию (GCSettings.LargeObjectHeapCompactionMode) — но это дорого и разово.

005Когда стоит использовать struct вместо class? Чем опасен mutable struct?▶

struct уместен для мелких (≲16–24 байта), неизменяемых, короткоживущих значений с семантикой значения (координаты, деньги, ключи), особенно в горячих путях, чтобы избежать аллокаций и нагрузки на GC.

Mutable struct опасен: при передаче в метод/добавлении в коллекцию/в свойство копируется, и изменения уходят в копию, а не в оригинал — источник неочевидных багов. Также struct в коллекции List возвращается копией. Правило: делать struct readonly и неизменяемыми.

006Что такое Span<T> и Memory<T>, какие задачи они решают?▶

Span<T> — типобезопасное «окно» в непрерывную область памяти (массив, stackalloc, нативная память) без аллокаций и копирования. Позволяет слайсить, парсить, обрабатывать данные zero-allocation. Это ref struct — живёт только на стеке, нельзя положить в поле класса, использовать в async или захватить замыканием.

Memory<T> снимает эти ограничения (можно хранить в поле, передавать в async), а .Span даёт доступ к данным в нужный момент. Применение: высокопроизводительный парсинг, сериализация, работа с буферами без лишних аллокаций.

007Объясни разницу между IEnumerable, ICollection, IList и IReadOnlyList.▶

IEnumerable<T> — только итерация (forward-only), основа LINQ, поддерживает ленивость. ICollection<T> добавляет Count, Add/Remove, Contains. IList<T> добавляет доступ по индексу и Insert/RemoveAt. IReadOnlyList<T> — индекс и Count, но без мутаций (read-only контракт).

На практике: принимай параметром самый узкий интерфейс (IEnumerable, если только перебираешь), возвращай IReadOnlyList/IReadOnlyCollection, чтобы не давать вызывающему менять внутреннее состояние.

008Как работает yield return? Что такое отложенное выполнение (deferred execution)?▶

yield return заставляет компилятор сгенерировать конечный автомат (state machine), реализующий IEnumerator: тело метода выполняется порциями при каждом MoveNext(), сохраняя состояние между вызовами.

Deferred execution: код итератора (и большинство LINQ-операторов) не выполняется в момент вызова, а только при переборе. Следствия: запрос может выполниться несколько раз, исключения вылетают при итерации, а не при создании. Для фиксации результата используют ToList()/ToArray().

009Что делают using и IDisposable? Зачем нужен финализатор?▶

IDisposable.Dispose() — детерминированное освобождение неуправляемых ресурсов (файлы, сокеты, соединения). using — синтаксис, гарантирующий вызов Dispose через try/finally даже при исключении (using var x = ...; или блок).

Финализатор (~Type()) — страховка: если Dispose забыли вызвать, GC всё же освободит неуправляемый ресурс. Но финализация недетерминирована, замедляет GC (объект переживает лишнюю сборку), поэтому нужна только классам, владеющим неуправляемыми хэндлами напрямую; обычно лучше SafeHandle.

010В чём разница между Dispose и финализатором? Что такое Dispose pattern?▶

Dispose вызывается явно/через using, детерминированно, может освобождать и управляемые, и неуправляемые ресурсы. Финализатор вызывает GC недетерминированно и только для неуправляемых (управляемые уже могут быть собраны).

Dispose pattern: protected virtual void Dispose(bool disposing). При disposing==true (явный вызов) освобождаем и управляемые, и неуправляемые; при false (из финализатора) — только неуправляемые. Публичный Dispose() вызывает Dispose(true) и GC.SuppressFinalize(this), чтобы снять объект с очереди финализации.

011Что такое замыкания (closures) и как они могут привести к утечкам памяти?▶

Замыкание — лямбда, захватывающая переменные окружения. Компилятор генерирует класс-«display class», где захваченные переменные становятся полями, продлевая их время жизни до времени жизни делегата.

Утечки: если делегат с замыканием подписан на долгоживущее событие (или хранится в статике/кэше), он удерживает захваченный this и связанные объекты — классическая утечка через события (надо отписываться). Также скрытые аллокации: замыкание в горячем цикле создаёт объект на каждой итерации.

012Чем отличается const от readonly и когда что использовать?▶

const — compile-time константа, встраивается (inlining) в место использования, только примитивы/строки/null. Минус: при изменении значения в библиотеке потребители должны быть перекомпилированы (versioning-проблема).

readonly — runtime, поле задаётся в объявлении или конструкторе, может быть любым типом, у каждого экземпляра своё значение (или static readonly — общее). Правило: const только для вечных констант (Pi, дни недели); для публичных API и вычисляемых/возможно меняющихся значений — readonly.

013Что такое методы-расширения и как компилятор их резолвит?▶

Метод-расширение — static метод в static классе с this у первого параметра; вызывается как метод экземпляра. Компилятор при ненахождении инстанс-метода ищет extension-методы в импортированных (using) namespace'ах и подставляет статический вызов.

Нюансы: инстанс-методы всегда приоритетнее; расширения не видят private-члены; нельзя переопределить существующий метод; на null-ссылке extension вызвать можно (это просто статический вызов). LINQ целиком построен на extension-методах над IEnumerable.

014Объясни ковариантность и контравариантность дженериков (in/out).▶

Ковариантность (out) — можно использовать более производный тип: IEnumerable<string> присваивается IEnumerable<object> (тип только «выходит»). Контравариантность (in) — наоборот, более базовый: Action<object> присваивается Action<string> (тип только «входит»).

out разрешён, если параметр используется только в возвращаемых позициях, in — только во входных. Применимо к интерфейсам и делегатам (не к классам). Примеры: IEnumerable<out T>, IComparer<in T>, Func<in T,out TResult>.

015Что такое expression trees и где они применяются (например, в EF Core)?▶

Expression tree — представление кода как данных: лямбда типа Expression<Func<T,bool>> компилируется не в делегат, а в дерево узлов, которое можно анализировать и преобразовывать в рантайме.

EF Core разбирает дерево Where(x => x.Age > 18) и транслирует его в SQL. Также используется в мапперах, валидаторах, DI-контейнерах, динамическом построении запросов. Можно строить деревья вручную (Expression.Lambda) и компилировать (.Compile()) для быстрых динамических вызовов.

016Почему string иммутабельна? Что такое string interning?▶

Иммутабельность строк даёт потокобезопасность (можно шарить без блокировок), безопасное использование как ключей словарей/хэшей, и возможность интернирования. Любая «модификация» создаёт новую строку.

String interning — пул уникальных строковых литералов: одинаковые литералы ссылаются на один объект в памяти, экономя её. Строки из кода интернируются автоматически; для рантайм-строк есть string.Intern. Для активной конкатенации в цикле используют StringBuilder, чтобы не плодить промежуточные строки.

017Что такое record и чем он отличается от class? Что такое value equality?▶

record (ссылочный, либо record struct) — синтаксический сахар для типов-значений по содержимому: компилятор генерирует Equals/GetHashCode по всем полям (value equality), ToString, деконструктор и with-выражения для неразрушающего копирования.

Отличие от обычного class: класс сравнивается по ссылке, record — по значению полей. Records задуманы для иммутабельных DTO/value object'ов (init-сеттеры, позиционный синтаксис). Наследование у records поддерживается и учитывается в равенстве (сравнивается и EqualityContract).

018Что такое pattern matching и какие виды паттернов есть в C#?▶

Pattern matching — проверка структуры/типа значения с извлечением данных в is, switch-выражениях и операторах. Виды: type (is Customer c), constant (is null, is 0), relational (> 100), logical (and/or/not), property ({ Age: > 18, Name.Length: > 0 }), positional (через деконструктор), list patterns ([1, .., 5]), var и discard (_).

Упрощает ветвление, заменяет цепочки if/cast и делает switch-выражения декларативными.

019Чем отличается Task от ValueTask и когда ValueTask оправдан?▶

Task — ссылочный тип, его создание — аллокация в куче. ValueTask — struct, который может обернуть либо уже готовый результат (без аллокации), либо Task для реально асинхронного пути.

ValueTask оправдан в горячих путях, где результат часто доступен синхронно (кэш-хит, буферизованный поток) — экономит аллокации. Ограничения: нельзя ждать дважды, нельзя .Result до завершения, нельзя хранить/комбинировать как Task. Если не уверены — используйте Task; ValueTask — точечная оптимизация по результатам профилирования.

020Что важного появилось в последних версиях .NET (например, .NET 8) и что из этого ты используешь?▶

.NET 8 (LTS): Native AOT (быстрый старт, меньше памяти, для контейнеров/CLI), keyed services в DI, улучшения Minimal API и IExceptionHandler, frozen collections (FrozenDictionary), TimeProvider для тестируемого времени, рост производительности рантайма и JIT (dynamic PGO), primary constructors и collection expressions в C# 12.

На практике использую: keyed services для стратегий, TimeProvider вместо DateTime.Now, frozen-коллекции для статичных справочников, AOT-сборки для лёгких сервисов, и регулярно поднимаю TFM ради бесплатного прироста производительности рантайма.

021Как async/await работает под капотом (state machine)?▶
  1. async/await — это синтаксический сахар: компилятор переписывает async-метод в конечный автомат (state machine), где поле _state помнит, на каком шаге метод остановился, а локальные переменные превращаются в поля, чтобы пережить приостановку.
  2. Метод разрезается по точкам await, и весь его код раскладывается в метод MoveNext(), который вызывается несколько раз — по куску за вызов.
  3. Встретив незавершённую задачу, await не блокирует и не создаёт поток, а регистрирует колбэк «позови меня снова, когда будет готово» и отпускает текущий поток; когда задача завершается, колбэк снова вызывает MoveNext(), и автомат продолжает с места остановки.
  4. Если задача в момент await уже готова (IsCompleted == true), всё идёт дальше синхронно — без приостановки и аллокаций, поэтому правильный async почти бесплатен на горячем пути.
  5. Пока приостановок нет, автомат живёт на стеке; при первой реальной приостановке он уезжает в кучу (плюс аллоцируются Task и колбэк) — отсюда смысл ValueTask для экономии и причина, почему ref struct вроде Span<T> нельзя протащить через await.
  6. Куда вернётся продолжение, решает SynchronizationContext/TaskScheduler, и именно этим управляет ConfigureAwait(false).
022Что такое SynchronizationContext и как он влияет на продолжение после await?▶

SynchronizationContext абстрагирует «куда вернуть выполнение». По умолчанию await захватывает текущий контекст и возобновляет продолжение в нём. В UI (WinForms/WPF) это UI-поток, что нужно для доступа к контролам.

В ASP.NET Core контекста нет (его убрали), поэтому продолжения идут на любом потоке из пула — поэтому ConfigureAwait(false) там не обязателен, но полезен в библиотеках. Захват контекста — частая причина deadlock при блокирующих вызовах async-кода.

023Зачем нужен ConfigureAwait(false) и где его применять?▶

ConfigureAwait(false) говорит «не захватывать SynchronizationContext, продолжить на любом потоке пула». Это убирает риск deadlock при смешении с блокирующим кодом и снижает накладные расходы на маршалинг в контекст.

Применять в библиотечном коде, который не зависит от контекста. В коде приложения ASP.NET Core это не нужно (контекста нет), но и не вредит. В UI-коде на верхнем уровне обработчика, наоборот, контекст нужен. Правило: библиотеки — false, прикладной UI-код — оставлять контекст.

024Как возникает deadlock при вызове .Result/.Wait() на async-коде?▶

Классика в среде с SynchronizationContext (UI, старый ASP.NET): поток вызывает task.Result и блокируется, ожидая задачу. Задача внутри делает await и хочет вернуть продолжение в тот же (уже заблокированный) контекст → взаимоблокировка.

Лечение: «async all the way» — не смешивать блокирующие вызовы с async, использовать await вместо .Result/.Wait(); в библиотеке — ConfigureAwait(false). В ASP.NET Core контекста нет, поэтому такой deadlock не возникает, но .Result всё равно вреден (блокирует поток пула, риск starvation).

025В чём разница между Thread, Task и ThreadPool?▶

Thread — реальный поток ОС, дорогой (≈1 МБ стека, контекст-свитчи); создавать вручную стоит только для долгоживущих выделенных задач. ThreadPool — переиспользуемый пул потоков, амортизирует создание; на нём исполняются короткие рабочие элементы. Task — абстракция над единицей работы (обычно поверх ThreadPool), даёт композицию, продолжения, отмену, результат и исключения.

Практика: для CPU-работы — Task.Run (пул), для I/O — async/await без занятия потоков, отдельный Thread — редкое исключение.

026Что такое race condition? Приведи пример и способ решения.▶

Race condition — результат зависит от недетерминированного порядка доступа потоков к общему состоянию. Пример: counter++ из двух потоков — это read-modify-write, инкременты теряются.

Решения: блокировки (lock), атомарные операции (Interlocked.Increment), иммутабельность, потокобезопасные коллекции, или вообще не делить состояние (разделение по потокам/акторам). Выбор — самый дешёвый вариант, дающий нужную корректность; для простого счётчика — Interlocked.

027Какие примитивы синхронизации знаешь (lock, Monitor, SemaphoreSlim, Mutex) и когда что?▶

lock/Monitor — внутрипроцессное взаимоисключение, дёшево, но только для синхронного кода (нельзя await внутри). SemaphoreSlim — ограничение конкурентности N, поддерживает WaitAsync → единственный выбор для async-критических секций. Mutex — межпроцессный (named), дорогой, для координации между процессами/инстансами на одной машине. ReaderWriterLockSlim — много читателей / один писатель.

Правило: один процесс синхронно → lock; async → SemaphoreSlim(1,1); между процессами → Mutex; между сервисами → распределённая блокировка (Redis).

028Чем lock отличается от SemaphoreSlim в асинхронном коде?▶

lock компилируется в Monitor.Enter/Exit и привязан к потоку — внутри него нельзя делать await (продолжение может уйти на другой поток, а Monitor требует освобождения тем же потоком). SemaphoreSlim не привязан к потоку и имеет WaitAsync(), поэтому подходит для защиты async-секций.

Паттерн: await _sem.WaitAsync(); в try, _sem.Release() в finally. Для счётчика 1/1 это асинхронный аналог lock.

029Что делает volatile и зачем нужен memory barrier?▶

volatile запрещает компилятору/процессору переупорядочивать и кэшировать чтения/записи поля: запись имеет release-семантику, чтение — acquire. Это гарантирует видимость последнего значения между потоками, но не атомарность составных операций.

Memory barrier (Thread.MemoryBarrier, Interlocked) запрещает переупорядочивание операций памяти через барьер. Нужны из-за оптимизаций и слабых моделей памяти. На практике volatile используют редко; чаще берут Interlocked или lock, которые дают полную семантику.

030Что такое Interlocked и какие операции он предоставляет?▶

Interlocked — набор атомарных операций без блокировок (lock-free), реализованных через инструкции процессора: Increment/Decrement, Add, Exchange (атомарная замена), CompareExchange (CAS — заменить, если значение совпало), Read для 64-бит на 32-бит платформах.

Используется для счётчиков, флагов, lock-free структур и паттерна optimistic update в цикле на CAS. Быстрее lock, но применим только к простым атомарным изменениям одной переменной.

031Как отменить асинхронную операцию и корректно пробросить CancellationToken?▶

Через CancellationTokenSource → token, который пробрасывается во все асинхронные вызовы по цепочке. Операции проверяют token.ThrowIfCancellationRequested() или передают токен в I/O-методы; при отмене вылетает OperationCanceledException.

Хорошие практики: всегда принимать CancellationToken параметром (последним), пробрасывать дальше, использовать CreateLinkedTokenSource для комбинирования (например, таймаут + клиентская отмена), не «глотать» OperationCanceledException. В ASP.NET Core доступен HttpContext.RequestAborted.

032Какие потокобезопасные коллекции знаешь и как устроен ConcurrentDictionary?▶

System.Collections.Concurrent: ConcurrentDictionary, ConcurrentQueue, ConcurrentStack, ConcurrentBag, BlockingCollection. ConcurrentDictionary использует разбиение на блокировки (lock striping): несколько внутренних замков на бакеты, поэтому записи в разные бакеты идут параллельно; чтения в основном lock-free.

Важно: GetOrAdd/AddOrUpdate атомарны на уровне словаря, но переданная фабрика может вызваться несколько раз при гонке — её делают идемпотентной или используют Lazy<T> как значение.

033Что такое Channel<T> и для каких сценариев он подходит?▶

Channel<T> — высокопроизводительная async очередь producer/consumer с поддержкой WaitToReadAsync/ReadAllAsync и backpressure (bounded канал блокирует продюсера при переполнении). Это современная замена BlockingCollection для async-кода.

Сценарии: фоновая обработка (приём задач в BackgroundService), пайплайны, развязка скорости продюсера и консьюмера, ограничение конкурентности. Поддерживает single/multi producer/consumer режимы для оптимизации.

034Чем параллелизм отличается от конкурентности?▶

Конкурентность (concurrency) — структурирование программы так, чтобы много задач прогрессировали в перекрывающиеся периоды (но не обязательно одновременно); про управление несколькими делами сразу. Параллелизм (parallelism) — физически одновременное выполнение на нескольких ядрах.

I/O-bound задачи выигрывают от конкурентности (async/await освобождает поток на время ожидания), CPU-bound — от параллелизма (Parallel, PLINQ, Task.Run по ядрам). Можно иметь конкурентность без параллелизма (одно ядро, кооперативное переключение).

035Что такое thread pool starvation и как его диагностировать?▶

Голодание пула — все потоки ThreadPool заняты (часто блокирующими вызовами .Result/.Wait()/lock на долгие операции), новые рабочие элементы стоят в очереди, latency растёт. Пул добавляет потоки медленно (≈1 в ~0.5–1 с), поэтому деградация затяжная.

Диагностика: рост очереди ThreadPool, признаки в dotnet-counters (ThreadPool Queue Length, рост числа потоков), дампы с множеством потоков в ожидании. Лечение: убрать блокировку async-кода, делать «async all the way», вынести истинно блокирующие операции, ограничить конкурентность семафором.

036Расскажи про реальный баг с гонкой/синхронизацией, который ты чинил.▶

Структура ответа (STAR): опиши симптом (плавающие ошибки/дубли только под нагрузкой), как локализовал (логи с трассировкой, воспроизведение нагрузочным тестом, анализ общего состояния), корневую причину (например, non-atomic check-then-act над кэшем или двойная обработка сообщения без идемпотентности).

Хороший пример: ленивая инициализация кэша без синхронизации приводила к дублям → заменил на ConcurrentDictionary.GetOrAdd с Lazy<Task> (single-flight), добавил идемпотентный ключ. Подчеркни вывод: чинил причину, а не симптом, и добавил тест на гонку.

037Как устроен middleware pipeline и в каком порядке выполняются middleware?▶

Pipeline — цепочка делегатов RequestDelegate, каждый получает HttpContext и ссылку на next. Запрос идёт сверху вниз до терминального middleware, ответ — обратно вверх (модель «луковицы»). Порядок регистрации в app.Use... определяет порядок выполнения.

Типовой порядок: ExceptionHandler → HSTS/HTTPS redirect → Static files → Routing → CORS → Authentication → Authorization → Endpoints. Middleware может закоротить цепочку (не вызвать next) или выполнить код до и после next.

038Какие бывают lifetimes у сервисов в DI (singleton/scoped/transient)? Приведи пример ошибки.▶

Singleton — один экземпляр на всё приложение; Scoped — один на scope (в вебе — на HTTP-запрос); Transient — новый при каждом резолве. DbContext регистрируется как scoped.

Классическая ошибка — captive dependency: внедрить scoped (или transient) сервис в singleton. Singleton захватит первый экземпляр scoped навсегда, что ломает время жизни (например, один DbContext на всё приложение → гонки, утечки, устаревшие данные). Контейнер ловит часть таких ошибок при ValidateScopes.

039Что такое captive dependency и как её избежать?▶

Captive dependency — когда долгоживущий сервис удерживает короткоживущую зависимость, фактически продлевая ей жизнь. Пример: scoped DbContext, внедрённый в singleton, становится «вечным» и расшаривается между запросами/потоками.

Избегать: не внедрять scoped/transient в singleton напрямую; вместо этого внедрять IServiceScopeFactory и создавать scope на каждую операцию (using var scope = factory.CreateScope();), либо IServiceProvider, либо фабрику. Включить ValidateScopes/ValidateOnBuild, чтобы ловить нарушения на старте.

040Чем IHostedService отличается от BackgroundService?▶

IHostedService — базовый контракт с StartAsync/StopAsync, которые хост вызывает при запуске/остановке. BackgroundService — абстрактный класс, реализующий IHostedService и дающий единственный метод ExecuteAsync(CancellationToken) для длительной фоновой работы (цикл обработки).

Для долгоживущего воркера наследуют BackgroundService. Важно: тяжёлую работу нельзя делать в StartAsync (блокирует старт приложения), и нужно корректно реагировать на токен в ExecuteAsync для graceful shutdown.

041Как устроена конфигурация в ASP.NET Core? Что такое Options pattern?▶

Конфигурация — слоистая: провайдеры (appsettings.json, appsettings.{Env}.json, переменные окружения, command line, user secrets, key vault) накладываются по порядку, последний выигрывает. Доступ через IConfiguration.

Options pattern — типобезопасная проекция секции конфига на POCO через IOptions<T> (singleton, фиксируется на старте), IOptionsSnapshot<T> (scoped, перечитывает на запрос) и IOptionsMonitor<T> (singleton с уведомлениями о hot-reload). Поддерживает валидацию (ValidateDataAnnotations, ValidateOnStart).

042Как работают model binding и валидация и как их кастомизировать?▶

Model binding мапит данные запроса (route, query, form, body, header) на параметры/модели action'а по соглашениям и атрибутам ([FromBody], [FromQuery]...). Затем срабатывает валидация по DataAnnotations, результат — в ModelState.

Кастомизация: свои IModelBinder/IModelBinderProvider, кастомные ValidationAttribute или IValidatableObject, либо вынос валидации в FluentValidation. Для API [ApiController] автоматически возвращает 400 с ValidationProblemDetails при невалидной модели.

043Чем фильтры отличаются от middleware и какие виды фильтров есть?▶

Middleware работает на уровне всего pipeline и не знает про MVC/routing-детали. Фильтры работают внутри MVC-пайплайна и имеют доступ к контексту action'а (модель, результат, выбранный метод). Виды: Authorization, Resource, Action, Exception, Result — в этом порядке вокруг выполнения action.

Выбор: кросс-каттинг для всех запросов (логирование, заголовки) — middleware; логика, привязанная к action/модели (валидация, кэширование результата, обработка исключений контроллеров) — фильтры.

044Как реализуются аутентификация и авторизация (JWT, политики, роли)?▶

Аутентификация устанавливает «кто ты» (ClaimsPrincipal); для API обычно JWT Bearer: AddAuthentication().AddJwtBearer(...) валидирует подпись, issuer, audience, срок. Авторизация решает «что можно».

Подходы: по ролям ([Authorize(Roles=...)]), по политикам (AddPolicy с требованиями IAuthorizationRequirement + AuthorizationHandler для сложной логики), и resource-based (IAuthorizationService.AuthorizeAsync для проверки прав на конкретный объект). Политики гибче ролей и предпочтительны.

045Что такое Kestrel и зачем перед ним обратный прокси?▶

Kestrel — кросс-платформенный высокопроизводительный встроенный веб-сервер ASP.NET Core, может работать как edge-сервер напрямую. Обратный прокси (Nginx, YARP, IIS, ingress) ставят перед ним для TLS-терминации, балансировки, буферизации медленных клиентов (защита от slowloris), статики, rate limiting, единой точки маршрутизации.

При работе за прокси нужно настроить ForwardedHeaders, чтобы корректно получать реальный IP клиента и схему (X-Forwarded-For/-Proto).

046Как обрабатывать ошибки глобально (exception middleware, ProblemDetails)?▶

Глобально — через UseExceptionHandler (ловит необработанные исключения, логирует, возвращает безопасный ответ без утечки стектрейса). В .NET 8+ удобен IExceptionHandler для маппинга типов исключений на статусы.

Формат ответа стоит унифицировать через ProblemDetails (RFC 7807): AddProblemDetails() даёт машиночитаемые ошибки (type/title/status/detail/traceId). Бизнес-исключения мапятся на 4xx, неожиданные — на 500 с корреляционным id для поиска в логах.

047Minimal API против контроллеров — что выбрать и почему?▶

Minimal API — меньше церемоний, ниже накладные расходы, хорошо для небольших сервисов, микросервисов, простых эндпоинтов; группировка через MapGroup, фильтры через AddEndpointFilter. Контроллеры — структурированность, привычные фильтры/атрибуты, model binding, удобнее для крупных API с множеством эндпоинтов и сложной кросс-каттинг логикой.

Выбор по масштабу и команде: маленький/перформанс-чувствительный сервис — minimal; большое приложение с богатой конвенцией — контроллеры. Производительность сейчас сопоставима; решает читаемость и поддержка.

048Как организовать graceful shutdown приложения?▶

Хост слушает SIGTERM/Ctrl+C и запускает graceful shutdown: перестаёт принимать новые соединения, даёт текущим запросам доиграться в пределах таймаута (HostOptions.ShutdownTimeout), вызывает StopAsync у hosted-сервисов, токены отмены срабатывают.

Практика: реагировать на CancellationToken в BackgroundService, дослать/закоммитить сообщения очередей, в Kubernetes согласовать terminationGracePeriodSeconds и preStop-хук (плюс readiness=false), чтобы балансировщик увёл трафик до завершения. Цель — ноль потерянных/оборванных запросов при деплое.

049Как работает change tracking в EF Core?▶

DbContext хранит снимок загруженных сущностей и отслеживает их состояние: Added, Unchanged, Modified, Deleted, Detached. При SaveChanges EF сравнивает текущие значения со снимком и генерирует нужные INSERT/UPDATE/DELETE.

Трекинг стоит памяти и CPU. Для read-only запросов используют AsNoTracking. Также есть ChangeTracker.DetectChanges (вызывается автоматически), который и выявляет изменения; при массовых операциях это узкое место.

050Что такое проблема N+1, как её обнаружить и решить?▶

N+1 — один запрос за списком + по запросу за связанными данными каждого элемента (например, lazy loading навигаций в цикле) → N+1 обращений к БД, высокая latency.

Обнаружение: логирование SQL EF Core, профайлер БД, APM-трейсы (много мелких одинаковых запросов). Решение: Include/ThenInclude (eager loading), проекция в DTO через Select (грузим только нужное одним запросом), AsSplitQuery при раздувании join'ов. Часто отключают lazy loading, чтобы N+1 не возникал незаметно.

051Когда использовать AsNoTracking и что он даёт?▶

AsNoTracking отключает change tracking для запроса: сущности не кладутся в трекер, нет снимков и identity resolution. Это быстрее и экономит память — идеально для read-only сценариев (отдача данных в API, отчёты).

Нюанс: без трекинга одинаковые записи могут стать разными инстансами (нет identity map); если нужна идентичность — AsNoTrackingWithIdentityResolution. Менять и сохранять такие сущности нельзя без явного Attach/Update. Можно включить no-tracking по умолчанию через QueryTrackingBehavior.

052Как EF Core транслирует LINQ в SQL? Чем опасна client-side evaluation?▶

LINQ-запрос строится как expression tree; EF Core разбирает его и переводит в SQL целевого провайдера. То, что нельзя перевести (например, вызов произвольного C#-метода в Where), раньше молча выполнялось на клиенте.

Client-side evaluation опасна: EF мог вытащить всю таблицу в память и фильтровать в приложении → катастрофа по производительности. В современных версиях EF бросает исключение, если часть Where/Join непереводима (клиентская оценка разрешена только для финальной проекции Select). Решение — переписать на переводимые конструкции или считать на стороне БД.

053Чем отличаются lazy, eager и explicit loading?▶

Eager — связанные данные грузятся сразу через Include в одном (или split) запросе. Lazy — навигация грузится автоматически при первом обращении (требует прокси и virtual-навигаций), удобно, но провоцирует N+1. Explicit — ручная дозагрузка через context.Entry(x).Reference/Collection.Load(), когда нужно контролируемо.

На бэкенде обычно предпочитают eager/проекции и избегают lazy в горячих путях из-за скрытых запросов.

054Как управлять транзакциями в EF Core?▶

Один SaveChanges уже атомарен — все изменения в одной транзакции. Для объединения нескольких SaveChanges/команд — явная транзакция: using var tx = await ctx.Database.BeginTransactionAsync(); ... await tx.CommitAsync();.

Можно задать уровень изоляции, использовать savepoints, разделять транзакцию между EF и ADO.NET через общий DbConnection. Для устойчивости к транзиентным сбоям с execution strategy (retry) транзакции оборачивают в strategy.ExecuteAsync. Распределённые транзакции между сервисами — избегать (см. Saga/Outbox).

055Что такое optimistic concurrency и как реализовать через concurrency token/rowversion?▶

Оптимистичный контроль конкуренции — не блокируем строку, а при сохранении проверяем, не изменил ли её кто-то ещё. В EF помечают поле [ConcurrencyCheck] или используют rowversion/[Timestamp] (в PostgreSQL — xmin через IsRowVersion).

EF добавляет это значение в WHERE при UPDATE; если затронуто 0 строк — кто-то опередил → DbUpdateConcurrencyException, которое обрабатывают (перечитать, смержить, показать пользователю). Подходит для редких конфликтов; для частых — пессимистичные блокировки.

056Как безопасно делать миграции на проде (zero-downtime)?▶

Принцип — expand/contract (расширяй-сжимай), совместимость старой и новой версий кода со схемой одновременно. Сначала аддитивные изменения (новая nullable-колонка/таблица), деплой кода, который пишет в обе, бэкафилл данных, затем переключение на новое, и только потом удаление старого отдельной миграцией.

Практики: миграции применяются отдельным шагом пайплайна (а не Database.Migrate() на старте всех реплик), избегать долгих блокирующих DDL/индексов на больших таблицах (онлайн-индексы, батчи), тестировать на копии прод-данных, иметь план отката.

057Что такое split query и зачем он нужен?▶

При Include нескольких коллекций EF по умолчанию делает один JOIN, что вызывает cartesian explosion — дублирование строк и раздувание объёма данных. AsSplitQuery() разбивает на несколько отдельных SQL-запросов (по одному на коллекцию), избегая декартова произведения.

Минус split query — несколько round-trip'ов и отсутствие транзакционной согласованности между ними по умолчанию. Выбор по профилю: широкие коллекции → split; узкие → single. Можно задать поведение глобально.

058Как эффективно делать массовую вставку/обновление данных?▶

Стандартный SaveChanges по сущности на каждую строку медленный из-за change tracking и отдельных команд. Для больших объёмов: ExecuteUpdate/ExecuteDelete (EF 7+, один SQL без загрузки в память), bulk-библиотеки (EFCore.BulkExtensions), SqlBulkCopy для SQL Server, либо raw SQL / COPY в PostgreSQL.

Если всё же через EF — отключить AutoDetectChanges, батчить, не держать десятки тысяч сущностей в одном контексте. Правило: для массовых операций обходить трекер.

059Почему DbContext должен быть scoped и почему его нельзя шарить между потоками?▶

DbContext — лёгкий, не потокобезопасный объект с состоянием (трекер изменений, открытое соединение). Один контекст = одна единица работы = один запрос/операция, поэтому регистрируется scoped.

Параллельное использование одного контекста из нескольких потоков (например, Task.WhenAll с запросами к одному контексту) ломает внутреннее состояние и бросает InvalidOperationException («second operation started»). Для параллелизма создают отдельные контексты (через IDbContextFactory) на каждую операцию.

060Как мапить наследование (TPH/TPT), owned types и value converters?▶

TPH (table-per-hierarchy) — вся иерархия в одной таблице с discriminator-колонкой; быстро, но много nullable-колонок. TPT — таблица на каждый тип с JOIN'ами; нормализованно, но медленнее. TPC — таблица на конкретный класс. По умолчанию EF использует TPH.

Owned types — value object'ы, встраиваемые в таблицу владельца (OwnsOne), без своего ключа. Value converters (HasConversion) преобразуют тип свойства в тип столбца (enum→string, типизированный id→Guid, шифрование), позволяя хранить богатые доменные типы.

📦 пэт-проект: EfCoreLab
061Как работают индексы (B-tree)? Чем составной индекс отличается от нескольких отдельных?▶

B-tree — сбалансированное дерево, дающее поиск/диапазон за O(log n) в отсортированном порядке. Индекс хранит ключи + указатели на строки, ускоряя WHERE/JOIN/ORDER BY ценой замедления записи и места.

Составной индекс (a,b,c) отсортирован по a, затем b, затем c — работает для условий по префиксу (a; a,b; a,b,c) и важен порядок колонок (leftmost prefix rule). Несколько отдельных индексов БД может объединить (index merge), но это обычно дороже одного хорошо подобранного составного под конкретный запрос.

062Что такое покрывающий индекс (covering index)?▶

Covering index содержит все колонки, нужные запросу (в ключе или во INCLUDE), поэтому БД отвечает прямо из индекса без обращения к самой таблице (index-only scan, без «lookup»/«key lookup»). Это убирает дорогой доступ к heap/clustered.

Применяют для горячих запросов: ключевые колонки — те, по которым фильтруют/сортируют, а возвращаемые-но-не-фильтруемые кладут в INCLUDE (SQL Server) или в конец ключа. Цена — больше места и нагрузка на запись.

063Как читать план запроса? Чем seq scan отличается от index scan?▶

План (EXPLAIN ANALYZE) показывает дерево операций, оценочные и фактические строки, стоимость и время. Читают снизу вверх; ищут расхождение estimate/actual (устаревшая статистика), дорогие seq scan на больших таблицах, nested loop с большим числом итераций, спиллы сортировок на диск.

Seq scan — последовательное чтение всей таблицы (хорошо при выборке большой доли строк или маленькой таблице). Index scan/seek — доступ через индекс (хорошо при селективном условии). Если ожидался индекс, а идёт seq scan — проблема селективности, статистики, приведения типов или отсутствия подходящего индекса.

064Какие есть уровни изоляции транзакций и какие аномалии каждый предотвращает?▶

Аномалии: dirty read, non-repeatable read, phantom read. Уровни: Read Uncommitted (ничего не гарантирует, допускает dirty read), Read Committed (нет dirty), Repeatable Read (нет non-repeatable), Serializable (нет фантомов, полная сериализуемость).

Чем выше уровень — тем меньше аномалий, но больше блокировок/конфликтов и ниже параллелизм. По умолчанию в PostgreSQL/Oracle — Read Committed на основе MVCC; в SQL Server — тоже Read Committed (или RCSI). Выбор — компромисс между корректностью и пропускной способностью.

065Что такое deadlock в БД и как его диагностировать и избегать?▶

Deadlock — две транзакции взаимно держат блокировки, нужные друг другу (T1 держит A, ждёт B; T2 держит B, ждёт A). СУБД обнаруживает цикл и убивает одну транзакцию (deadlock victim).

Диагностика: deadlock graph (SQL Server Extended Events, log_lock_waits в PostgreSQL), логи. Избегать: захватывать ресурсы в едином порядке, держать транзакции короткими, снижать уровень изоляции где можно, правильные индексы (меньше блокируемых строк), и закладывать retry на deadlock в приложении.

066В чём разница между пессимистичной и оптимистичной блокировкой?▶

Пессимистичная — блокируем данные на время работы (SELECT ... FOR UPDATE), другие ждут. Гарантирует отсутствие конфликтов, но снижает параллелизм и рискует deadlock'ами; уместна при высокой конкуренции за одни строки.

Оптимистичная — не блокируем, при записи проверяем версию/timestamp (concurrency token); при конфликте — ошибка и повтор. Лучше масштабируется при редких конфликтах. Выбор: частые конфликты и короткие критические данные → пессимистичная; редкие → оптимистичная.

067Что такое MVCC (на примере PostgreSQL)?▶

MVCC (multiversion concurrency control) — каждая запись хранит версии строк с метками транзакций (xmin/xmax). Читатели видят снимок данных на момент начала своей транзакции и не блокируют писателей, писатели — читателей.

UPDATE создаёт новую версию строки, старая остаётся видимой для старых снимков. «Мёртвые» версии убирает VACUUM (иначе раздувание — bloat). Плюс — высокий параллелизм чтения/записи; минус — накладные расходы на хранение версий и обслуживание (autovacuum, wraparound).

068Когда денормализация оправдана?▶

Когда нормализованная схема даёт слишком дорогие JOIN'ы/агрегации на критичных по latency чтениях, а данные читаются гораздо чаще, чем пишутся. Денормализация (дублирование, предрасчёт, materialized views, счётчики) снижает стоимость чтения ценой усложнения записи и риска рассогласования.

Оправдана с измерениями: сначала индексы/оптимизация запроса, и только если не хватает — контролируемая денормализация с механизмом синхронизации (триггеры, события, фоновое обновление). Помнить о цене консистентности.

069Что такое партиционирование таблиц и когда оно помогает?▶

Разбиение большой таблицы на части (по диапазону дат, хэшу, списку) — логически одна таблица, физически несколько. Помогает: partition pruning (запрос трогает только нужные партиции), быстрое удаление старых данных (DROP PARTITION вместо массового DELETE), параллелизм, обслуживание по частям.

Эффективно, когда запросы фильтруют по ключу партиционирования и таблица действительно очень большая. Минусы: усложнение, неэффективность запросов без ключа партиции, ограничения на уникальные индексы. Это не замена индексам, а дополнение.

070Чем WHERE отличается от HAVING? Каков логический порядок выполнения SQL?▶

WHERE фильтрует строки до группировки, HAVING — группы после агрегации (может использовать SUM/COUNT). Логический порядок выполнения: FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT.

Отсюда следствия: алиасы из SELECT нельзя использовать в WHERE (SELECT вычисляется позже), оконные функции работают после GROUP BY, а фильтровать по агрегату можно только в HAVING (или через подзапрос).

071Что такое оконные функции? Приведи практический пример.▶

Оконные функции считают агрегат/ранг по «окну» строк (OVER (PARTITION BY ... ORDER BY ...)), не схлопывая строки, как GROUP BY. Примеры: ROW_NUMBER, RANK, LAG/LEAD, нарастающий итог SUM() OVER (ORDER BY ...).

SELECT user_id, amount,
  ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) rn
FROM payments;
-- rn=1 -> последний платёж каждого пользователя

Практика: дедупликация (взять последнюю запись), топ-N в группе, скользящие средние, сравнение с предыдущей строкой.

072Опиши свой пошаговый подход к оптимизации медленного запроса.▶

1) Воспроизвести и измерить (EXPLAIN ANALYZE, реальные параметры). 2) Прочитать план: где основное время — seq scan, дорогой join, сортировка/спилл, плохие оценки строк. 3) Проверить статистику и индексы (есть ли подходящий, селективен ли, нет ли приведения типов, ломающего индекс).

4) Переписать запрос: убрать SELECT *, лишние подзапросы, заменить на join/оконную функцию, добавить ограничивающий WHERE/LIMIT. 5) Добавить/поправить индекс (составной/covering). 6) Если упёрлись — денормализация/кэш/материализация. После каждого шага — замер. Цель — устранить корневую операцию, а не угадывать.

073В чём разница между кластерным и некластерным индексом (MS SQL)?▶

Кластерный индекс задаёт физический порядок строк таблицы — сами данные хранятся в листьях B-tree; он один на таблицу (обычно по первичному ключу). Некластерный — отдельная структура с ключами и указателями (на кластерный ключ или RID); их может быть много.

Поиск по некластерному, если не covering, делает дополнительный key lookup в кластерный для остальных колонок. Поэтому ключ кластерного индекса хотят узким, возрастающим и стабильным (иначе раздувает все некластерные и вызывает фрагментацию).

074Что такое connection pool и какие с ним проблемы под нагрузкой?▶

Открытие соединения с БД дорого, поэтому ADO.NET держит пул переиспользуемых соединений (на строку подключения). Open берёт из пула, Dispose возвращает.

Проблемы под нагрузкой: исчерпание пула (Timeout expired) из-за незакрытых соединений (забытый Dispose), долгих транзакций, блокирующего async-кода или маленького Max Pool Size. Также БД имеет лимит соединений — много инстансов × большой пул может его превысить (тогда ставят PgBouncer). Лечение: всегда освобождать соединения (короткий scope DbContext), держать транзакции короткими, тюнить размер пула и следить за метриками.

06ООП, SOLID, паттерны14 вопросов
📄 статья: SolidMap
075Сформулируй каждый принцип SOLID и приведи пример нарушения SRP.▶

SRP — у класса одна причина для изменения. OCP — открыт для расширения, закрыт для изменения. LSP — наследник заменяет базовый тип без поломки поведения. ISP — много узких интерфейсов лучше одного «толстого». DIP — зависим от абстракций, а не от конкретики.

Нарушение SRP: класс OrderService, который и считает заказ, и пишет в БД, и шлёт email, и форматирует PDF — у него четыре причины меняться. Рефакторинг: выделить расчёт, репозиторий, нотификатор, генератор документа, оркеструя их.

076Что такое Liskov Substitution на практике? Приведи пример нарушения.▶

LSP: объект подтипа должен подставляться вместо базового без нарушения контракта (предусловия не усиливать, постусловия не ослаблять, инварианты сохранять, не бросать новых исключений).

Классика — Square : Rectangle: установка ширины меняет и высоту, ломая код, рассчитывающий на независимость сторон. Или ReadOnlyList : List, бросающий исключение в Add — нарушает ожидание базового типа. Лечение: моделировать через композицию/правильные абстракции, а не натягивать наследование.

077Чем dependency inversion отличается от dependency injection?▶

Dependency Inversion (DIP) — принцип проектирования: модули верхнего уровня и детали зависят от абстракций, а не друг от друга; абстракции принадлежат верхнему уровню. Dependency Injection (DI) — техника/паттерн реализации: передача зависимостей извне (через конструктор/метод), а не создание их внутри (new).

DI — один из способов соблюсти DIP. Можно делать DI без следования DIP (внедрять конкретные классы) и наоборот. DI-контейнер лишь автоматизирует сборку графа зависимостей.

078Композиция против наследования — когда что выбирать?▶

Наследование выражает строгое «является» и переиспользует реализацию, но создаёт жёсткую связь, хрупкость базового класса и проблемы LSP. Композиция («has-a», делегирование) гибче: меняем поведение через подставляемые компоненты, легче тестировать и комбинировать.

Правило «favor composition over inheritance»: наследование — для истинных отношений типа и полиморфизма; всё остальное (переиспользование поведения, варьируемые стратегии) — композиция/интерфейсы. Глубокие иерархии наследования — запах.

079Объясни паттерн Strategy и приведи пример из своего кода.▶

Strategy инкапсулирует семейство взаимозаменяемых алгоритмов за общим интерфейсом, позволяя выбирать поведение в рантайме без if/switch. Клиент работает с абстракцией, конкретная стратегия внедряется.

Пример: IPriceCalculator с реализациями Regular/Vip/Promo, выбираемыми по типу клиента; или разные IPaymentProvider. В .NET 8 удобно через keyed services: GetRequiredKeyedService<IShipping>(method). Даёт OCP — новый вариант добавляется без правки существующего кода.

080Что такое Factory и Abstract Factory и когда они нужны?▶

Factory Method — метод/класс, инкапсулирующий выбор и создание конкретного объекта, скрывая new и логику выбора от клиента. Abstract Factory — фабрика, создающая семейства связанных объектов (например, набор UI-компонентов под платформу) через общий интерфейс.

Нужны, когда создание сложное/условное, должно быть подменяемым (тесты, плагины) или когда важно гарантировать совместимость группы объектов. В .NET часто заменяется DI-контейнером и фабричными делегатами (Func<T>, IHttpClientFactory).

081Что такое Decorator и где он используется в .NET?▶

Decorator оборачивает объект тем же интерфейсом, добавляя поведение (логирование, кэширование, retry, валидацию) без изменения исходного класса и без наследования — динамически и композируемо.

В .NET: потоки (BufferedStream, GZipStream оборачивают Stream), DelegatingHandler в HttpClient pipeline, middleware-«луковица», поведения MediatR. С DI декораторы регистрируют вручную или через Scrutor (services.Decorate<IService, CachingService>()).

082Объясни Repository и Unit of Work. Нужны ли они поверх EF Core?▶

Repository абстрагирует доступ к данным (коллекция доменных объектов), Unit of Work объединяет изменения в одну атомарную транзакцию. Цель — изоляция домена от деталей персистентности и тестируемость.

Поверх EF Core они часто избыточны: DbContext уже UoW, а DbSet — repository, и оба легко мокаются/тестируются (InMemory, Testcontainers). Свой generic-репозиторий часто лишь прячет мощь LINQ. Применять стоит, если нужно скрыть EF от домена в Clean Architecture, унифицировать запросы или поддержать несколько источников. Иначе — лишний слой.

083Что такое Mediator (и MediatR)? Плюсы и минусы подхода.▶

Mediator централизует взаимодействие: отправитель шлёт сообщение (команду/запрос), посредник находит обработчик — объекты не знают друг о друге. MediatR реализует это в .NET: IRequest/IRequestHandler + pipeline behaviors (валидация, логирование, транзакции).

Плюсы: развязка контроллеров и логики, единое место для кросс-каттинга, удобно с CQRS. Минусы: косвенность (тяжелее проследить поток), оверхед на простых случаях, «магия» рефлексии, риск превратить всё в анемичные хендлеры. Хорош в средних/крупных приложениях, избыточен в маленьких.

084Что такое Observer / publish-subscribe?▶

Observer: субъект уведомляет подписчиков об изменении состояния, не зная их конкретики (one-to-many). Pub/Sub — обобщение через брокер/шину: издатели и подписчики полностью развязаны и не знают друг о друге, общаются через каналы/топики.

В .NET: события (event), IObservable<T>/Rx, INotificationHandler MediatR (внутрипроцессно), и брокеры сообщений (Kafka/RabbitMQ) для межсервисного pub/sub. Даёт слабую связность, но усложняет отладку и порядок/гарантии доставки.

085Что такое антипаттерны God Object и anemic domain model?▶

God Object — класс, который знает и делает слишком много (сотни методов, всё состояние системы): нарушает SRP, невозможно тестировать и менять. Лечение — декомпозиция по ответственностям.

Anemic domain model — сущности это только наборы геттеров/сеттеров без поведения, а вся логика в «сервисах». Формально ООП, но фактически процедурный стиль; бизнес-правила размазаны и дублируются. Богатая доменная модель держит данные и инварианты вместе (методы, меняющие состояние с проверками). Иногда анемичная модель уместна (простой CRUD), но для сложного домена это запах.

086Что такое DRY, KISS, YAGNI и когда они начинают вредить?▶

DRY — не дублируй знание. KISS — делай проще. YAGNI — не строй то, что пока не нужно.

Вредят при догматизме: DRY — преждевременное объединение случайно похожего кода создаёт неверную абстракцию и связность (лучше «дублировать, пока не ясна абстракция»); KISS — упрощение в ущерб необходимой надёжности/расширяемости; YAGNI — отказ от заведомо нужной точки расширения, ведущий к дорогому переписыванию. Это эвристики, а не законы — применять с учётом контекста и стоимости изменения.

087Чем агрегат отличается от сущности в DDD?▶

Сущность (entity) — объект с идентичностью, живущей во времени (Order, User). Агрегат (aggregate) — кластер сущностей и value object'ов, рассматриваемый как единое целое для изменений, с корнем (aggregate root) — единственной точкой входа, через которую соблюдаются инварианты.

Правила: ссылки извне — только на корень (по id), транзакционная граница = один агрегат за транзакцию, согласованность внутри агрегата сильная, между агрегатами — eventual через доменные события. Агрегат держат маленьким.

088Что такое иммутабельность и почему она упрощает многопоточность?▶

Иммутабельный объект не меняется после создания: любое «изменение» порождает новый объект. В C# — readonly поля, init-сеттеры, record, иммутабельные коллекции.

Для многопоточности это убирает целый класс проблем: нет общего изменяемого состояния → нет гонок и не нужны блокировки при чтении, объект можно свободно шарить между потоками. Цена — аллокации при «изменении» (частично решается structural sharing в persistent-коллекциях). Это основа функционального стиля и безопасного параллелизма.

07Архитектура: DDD, Clean, CQRS12 вопросов
📦 пэт-проект: CleanLab
089Объясни Clean / гексагональную архитектуру. Куда направлены зависимости?▶

Слои: в центре домен (сущности, правила), вокруг — application (use cases), снаружи — инфраструктура и UI/API. Все зависимости направлены внутрь: внешние слои зависят от внутренних, а домен не знает ничего о БД, фреймворках, HTTP (Dependency Rule).

Гексагональная (ports & adapters) — то же через «порты» (интерфейсы, определённые внутри) и «адаптеры» (реализации снаружи: БД, очереди, REST). Инверсия зависимостей даёт тестируемость домена и заменяемость инфраструктуры без правки бизнес-логики.

090Что такое CQRS и когда стоит разделять команды и запросы?▶

CQRS — разделение модели на команды (меняют состояние, без возврата данных) и запросы (читают, без побочных эффектов). Можно иметь разные модели чтения/записи и даже разные хранилища.

Стоит, когда чтение и запись сильно асимметричны: разные нагрузки и масштабирование, сложная доменная запись против плоских read-моделей, потребность в денормализованных проекциях. Для простого CRUD это оверинжиниринг. Лёгкий вариант — просто разные модели команд/запросов без отдельных БД (часто с MediatR).

091Что такое Event Sourcing? Его плюсы и минусы.▶

Event Sourcing хранит не текущее состояние, а последовательность доменных событий; состояние восстанавливается их проигрыванием (replay). Снимки (snapshots) ускоряют восстановление.

Плюсы: полный аудит/история, time-travel, естественная интеграция с CQRS и проекциями, возможность пересчёта read-моделей. Минусы: высокая сложность, версионирование событий, eventual consistency проекций, трудные запросы по текущему состоянию, нельзя «просто поправить» данные. Применять точечно там, где история и аудит — часть домена (финансы, ledger), а не везде.

092Что такое bounded context в DDD?▶

Bounded context — явная граница, внутри которой модель и единый язык (ubiquitous language) согласованны и имеют единый смысл. Один термин («Customer») в разных контекстах (продажи, поддержка, биллинг) может означать разные модели.

Контексты соответствуют поддоменам и часто — границам сервисов/команд. Связи между ними описывают context map (shared kernel, customer-supplier, anti-corruption layer). Это инструмент против «одной модели на всё» и размывания смысла в больших системах.

093Что такое доменное событие и как его обрабатывать?▶

Доменное событие — факт, произошедший в домене и значимый для бизнеса (OrderPlaced), в прошедшем времени. Агрегат фиксирует события при изменении состояния, не выполняя побочные эффекты сам.

Обработка: события собирают и публикуют после успешного сохранения (часто в SaveChanges), внутрипроцессно через MediatR-нотификации или наружу через брокер. Для надёжной доставки наружу — Outbox pattern (событие пишется в ту же транзакцию, что и изменение). Это развязывает побочные эффекты и держит агрегат чистым.

094Где в слоистой архитектуре должна жить бизнес-логика?▶

В доменном слое: инварианты и правила — внутри сущностей/агрегатов и value object'ов (богатая модель), доменные сервисы — для логики, не принадлежащей одной сущности. Application-слой только оркеструет use case (загрузить агрегат, вызвать метод, сохранить), не содержа бизнес-правил.

Чего избегать: бизнес-логика в контроллерах, в SQL-запросах или «размазанная» по сервисам поверх анемичных сущностей. Контроллеры — тонкие, инфраструктура — заменяема, правила — в одном месте, где их легко тестировать.

095Как ты декомпозируешь монолит — по слоям или по фичам/доменам?▶

Предпочтительно по фичам/доменам (vertical slices / bounded contexts): каждый модуль владеет своим UI→логикой→данными, изменения локальны, меньше связности между модулями. Декомпозиция по техническим слоям (controllers/services/repositories) раскидывает одну фичу по всему коду и повышает связность.

Практически: сначала выделяю модули внутри монолита по доменам (modular monolith) с чёткими границами и контрактами, и только вызревшие, нагруженно-обособленные модули выношу в сервисы. Сервисная граница должна повторять доменную, а не наоборот.

096Что такое value object и зачем он нужен?▶

Value object — объект без идентичности, определяемый только своими значениями, иммутабельный, со сравнением по содержимому (Money, Email, DateRange, Address). Два VO равны, если равны их поля.

Зачем: инкапсулирует валидацию и инварианты в одном месте (нельзя создать невалидный Email), делает код выразительнее и типобезопаснее (вместо «голых» string/decimal), убирает дублирование правил. В C# удобно моделировать через record; в EF — как owned type.

097Что такое anti-corruption layer?▶

ACL — прослойка-переводчик между нашим bounded context и внешней системой/легаси с чужой моделью. Она конвертирует чужие понятия в наши и обратно, не давая «протечь» чужой модели и испортить нашу доменную.

Реализуется адаптерами/фасадами/мапперами на границе. Особенно важно при интеграции со старыми системами и сторонними API: домен остаётся чистым, а при смене внешней системы меняется только ACL.

098Как тестировать доменную логику изолированно от инфраструктуры?▶

Богатая доменная модель не зависит от БД/HTTP, поэтому тестируется как обычные объекты — без моков и I/O: создаём агрегат, вызываем метод, проверяем состояние/выброшенные доменные события/исключения. Это быстрые и стабильные unit-тесты.

Условие — соблюдённая инверсия зависимостей: домен оперирует интерфейсами (репозитории, время через TimeProvider), которые в тестах подменяются простыми заглушками. Инфраструктуру проверяют отдельными интеграционными тестами. Если для теста домена нужна БД — архитектура протекает.

099Что такое vertical slice architecture?▶

Организация кода по фичам (вертикальным срезам), а не по техническим слоям: всё для одной операции (endpoint, команда/запрос, валидация, доступ к данным) лежит вместе. Срезы независимы, поэтому изменение фичи затрагивает один срез, а не пять горизонтальных папок.

Хорошо сочетается с CQRS/MediatR: каждый срез — это handler. Минимизирует связность и абстракции «на всякий случай» (часто без generic-репозиториев). Минус — возможное дублирование между срезами, которое допускается осознанно.

100Когда CQRS и event sourcing превращаются в оверинжиниринг?▶

Когда сложность инструмента превышает сложность задачи: простой CRUD с симметричными чтением/записью, малой нагрузкой и без требований к аудиту/истории. Тогда отдельные модели, проекции, eventual consistency и инфраструктура событий добавляют когнитивную нагрузку и баги без выгоды.

Признаки оверинжиниринга: ES «потому что модно», команда не понимает версионирование событий, бизнес не требует истории, а консистентность read-моделей становится постоянным источником проблем. Начинать стоит с простого (один слой/CRUD), вводя CQRS/ES точечно по реальной необходимости.

📦 пэт-проект: OrderFlow
101Монолит против микросервисов — критерии выбора. Когда микросервисы вредят?▶

Микросервисы дают независимый деплой/масштабирование/команды и изоляцию отказов, но платят сетевой latency, распределёнными транзакциями, сложностью эксплуатации (observability, версионирование, тестирование). Критерии за: большая команда/несколько команд, разные требования к масштабированию частей, зрелая DevOps-культура, чёткие доменные границы.

Вредят при: маленькой команде, неясных границах (получится «распределённый монолит» с синхронными цепочками вызовов), отсутствии автоматизации/наблюдаемости, общей БД. Разумный путь — начать с modular monolith и выносить сервисы по мере реальной необходимости.

102Как обеспечить согласованность данных между сервисами (eventual consistency)?▶

Распределённых ACID-транзакций избегают; вместо этого — eventual consistency через асинхронные события: сервис атомарно меняет своё состояние и публикует событие, другие реагируют и обновляют свои данные. Согласованность достигается со временем.

Инструменты: Outbox (надёжная публикация), Saga (координация бизнес-процесса с компенсациями), идемпотентные обработчики (защита от дублей), версионирование/контракты событий. Бизнес должен принять временную рассинхронизацию; где нужна сильная согласованность — держать данные в одном сервисе/агрегате.

103Что такое паттерн Saga? Оркестрация против хореографии.▶

Saga — распределённая транзакция как последовательность локальных шагов; при сбое выполняются компенсирующие действия (откатывают предыдущие шаги семантически, т.к. настоящего rollback нет).

Оркестрация — центральный координатор (orchestrator) явно вызывает шаги и компенсации: проще отслеживать и менять процесс, но появляется центральная точка. Хореография — сервисы реагируют на события друг друга без центра: слабее связность, но логику процесса труднее увидеть и отлаживать. Выбор: сложные процессы — оркестрация; простые цепочки — хореография.

104Что такое Outbox pattern и какую проблему он решает?▶

Проблема dual write: нельзя атомарно и записать в БД, и опубликовать в брокер — если упасть между ними, состояние и события рассинхронизируются. Outbox решает это: событие пишется в таблицу outbox в той же транзакции, что и бизнес-изменение.

Отдельный процесс (relay/CDC, например Debezium) читает outbox и публикует в брокер, помечая отправленные. Гарантия — at-least-once (возможны дубли при ретраях), поэтому потребители обязаны быть идемпотентными. Это стандартный способ надёжной интеграции БД и очередей.

105Что такое идемпотентность и как обеспечить её при обработке сообщений?▶

Идемпотентность — повторная обработка того же сообщения даёт тот же результат без побочных дублей. Критична, потому что брокеры дают at-least-once (дубли неизбежны).

Способы: уникальный message/idempotency key и таблица обработанных сообщений (processed set) — перед обработкой проверяем, не видели ли уже; INSERT ... ON CONFLICT DO NOTHING/UPSERT; естественная идемпотентность операции (установка значения, а не инкремент); версии/условные апдейты. Ключ проверки и бизнес-эффект — в одной транзакции.

106Что такое circuit breaker, retry, timeout и bulkhead?▶

Timeout — не ждать ответа вечно, освобождать ресурсы. Retry — повтор транзиентной ошибки, обязательно с экспоненциальной задержкой и jitter (иначе retry storm). Circuit breaker — после серии ошибок «размыкает цепь» и быстро отклоняет запросы к больному сервису (closed→open→half-open), давая ему восстановиться. Bulkhead — изоляция ресурсов (пулов) по зависимостям, чтобы отказ одной не выел все потоки/соединения.

Вместе они предотвращают каскадные отказы. Retry без circuit breaker может добить падающий сервис.

107Как работает Polly и какие политики он предоставляет?▶

Polly — .NET библиотека устойчивости. Политики: Retry (с backoff/jitter), CircuitBreaker/AdvancedCircuitBreaker, Timeout, Bulkhead (ограничение параллелизма), Fallback (запасной результат), RateLimiter, и ResiliencePipeline (v8) для комбинирования.

Интегрируется с IHttpClientFactory (AddStandardResilienceHandler), оборачивая исходящие HTTP-вызовы. Применяют к ненадёжным внешним зависимостям; политики комбинируют (timeout внутри retry внутри circuit breaker). Важно настраивать осознанно: агрессивный retry усугубляет инциденты.

108Что такое распределённая трассировка (correlation / trace id)?▶

Один запрос проходит через много сервисов; чтобы связать всё в единую картину, генерируют trace id на входе и пробрасывают его (и span id для каждого шага) через заголовки (W3C traceparent). Каждый сервис добавляет свои span'ы.

Реализация — OpenTelemetry + бэкенд (Jaeger/Tempo/Zipkin); в .NET — Activity/ActivitySource, автоинструментирование HTTP/EF/брокеров. Trace id кладут и в логи (correlation id), чтобы из трейса прыгать в логи. Незаменимо для отладки latency и сбоев в распределённой системе.

109Что такое CAP-теорема? Что выберешь — CP или AP и почему?▶

CAP: при сетевом разделении (Partition) распределённая система может гарантировать либо Consistency (все видят свежие данные), либо Availability (отвечает всегда), но не оба. Поскольку partition в реальности неизбежен, выбор практически между CP и AP.

CP (отказать в ответе, но не отдать устаревшее) — для денег, остатков, бронирований. AP (ответить, возможно устаревшим, доспейся позже) — для лент, каталогов, аналитики. Выбор зависит от бизнес-требований конкретных данных; в одной системе разные части могут быть CP и AP. Дополнение — PACELC (даже без partition есть выбор latency vs consistency).

110Как версионировать API и контракты между сервисами?▶

REST: версия в URL (/v1/), заголовке или media type; держать обратную совместимость, добавлять поля аддитивно (не ломать существующие), депрекейтить с переходным периодом. Параллельно поддерживать N и N+1, мигрировать потребителей, потом гасить старое.

Сообщения/protobuf: только совместимые изменения (новые опциональные поля, не переиспользовать номера полей, не менять типы). Контракты фиксировать схемами (OpenAPI, protobuf, schema registry) и проверять contract tests. Принцип Postel: строгий на выходе, толерантный на входе.

111Что такое service discovery и API Gateway?▶

Service discovery — динамическое нахождение адресов инстансов сервисов (они эфемерны при автоскейлинге). Реализуется через реестр (Consul, Eureka) или платформенно — DNS/Service в Kubernetes. Бывает client-side и server-side.

API Gateway — единая точка входа для клиентов: маршрутизация к сервисам, агрегация, аутентификация, rate limiting, TLS, версионирование, кэш. Снимает кросс-каттинг с сервисов и прячет внутреннюю топологию. В .NET — YARP/Ocelot или облачные шлюзы. Риск — превратить шлюз в узкое место/God-компонент.

112Как бороться с каскадными отказами?▶

Каскад: один медленный сервис исчерпывает потоки/соединения вызывающего, тот тоже «зависает», и отказ распространяется вверх. Меры: timeout на все внешние вызовы, circuit breaker (быстро отказывать к больному), bulkhead (изоляция пулов), rate limiting и load shedding (сбрасывать лишнее), backpressure.

Плюс: ретраи с jitter и лимитом, graceful degradation (отдать кэш/частичный ответ), здоровые health-check'и и автоскейлинг. Главная идея — локализовать отказ и не дать ожиданию распространиться.

113Почему при at-least-once доставке обработчики обязаны быть идемпотентными?▶

At-least-once означает, что сообщение может быть доставлено более одного раза (повтор после сбоя ack'а, ребаланс, ретрай). Если обработчик не идемпотентен, повтор приведёт к двойному эффекту: двойное списание, дубль письма, задвоенная запись.

Exactly-once на уровне инфраструктуры в общем случае недостижим/дорог, поэтому практический путь — at-least-once доставка + идемпотентная обработка (dedup по ключу, UPSERT, processed-таблица). Это и есть «effectively-once».

114Как реализовать распределённую блокировку?▶

Нужна, когда только один инстанс должен выполнять операцию. Реализации: Redis (SET key val NX PX ttl с уникальным токеном и безопасным освобождением через Lua; для строгих гарантий — Redlock с оговорками), ZooKeeper/etcd (ephemeral nodes, consensus), БД (advisory locks в PostgreSQL, строка-лок).

Обязательно: TTL/lease (чтобы упавший владелец не держал лок вечно), уникальный токен (освобождать только свой лок, fencing token против устаревших владельцев). Лучше вообще проектировать так, чтобы распределённый лок был не нужен (партиционирование, идемпотентность, single-consumer).

115Что такое two-phase commit и почему его избегают в микросервисах?▶

2PC — атомарный коммит между несколькими ресурсами через координатора: фаза prepare (все голосуют «готов»), фаза commit/abort. Даёт сильную согласованность.

Избегают, потому что 2PC блокирующий (ресурсы залочены до решения), плохо масштабируется, чувствителен к падению координатора (участники зависают), снижает доступность и связывает сервисы синхронно. В микросервисах вместо него — Saga с компенсациями и eventual consistency, что доступнее и устойчивее, ценой отказа от мгновенной атомарности.

116Как организовать конфигурацию и секреты в распределённой системе?▶

Конфигурацию выносят из кода (12-factor): переменные окружения, ConfigMap, централизованные стора (Consul, Spring Cloud Config, Azure App Configuration) с возможностью hot-reload. Разделять по окружениям, версионировать, валидировать на старте.

Секреты — никогда в git/образах: хранить в Vault/Azure Key Vault/AWS Secrets Manager или Kubernetes Secrets (с шифрованием at-rest, RBAC), доставлять через CSI-драйвер/sidecar/переменные. Практики: ротация, аудит доступа, least privilege, отдельные секреты на окружение, шифрование в транзите и на диске.

117Чем Kafka отличается от RabbitMQ и когда выбрать что?▶

Kafka — распределённый лог: сообщения хранятся (retention), читаются по offset, высокий throughput, реплей истории, потоковая обработка, масштабирование партициями. Консьюмер сам двигает offset.

RabbitMQ — традиционный брокер (smart broker): гибкая маршрутизация (exchange/routing), per-message ack, приоритеты, TTL, удаление после доставки. Лучше для классических очередей задач, RPC, сложной маршрутизации. Выбор: event streaming/большие объёмы/реплей → Kafka; командные очереди задач/сложная маршрутизация/низкая latency на сообщение → RabbitMQ.

118Как устроены топики, партиции и offset'ы в Kafka?▶

Топик делится на партиции — независимые упорядоченные логи; партиция — единица параллелизма и порядка. Каждое сообщение в партиции имеет монотонный offset. Запись добавляется в конец (append-only).

Порядок гарантируется только внутри партиции, не по топику. Консьюмеры коммитят offset, фиксируя прогресс; могут перечитать с любого offset (реплей). Партиции реплицируются (leader/followers) для отказоустойчивости. Число партиций определяет максимальный параллелизм консьюмеров.

119Что такое consumer group и как распределяется нагрузка между консьюмерами?▶

Consumer group — набор консьюмеров, совместно читающих топик. Каждая партиция в группе закреплена ровно за одним консьюмером, поэтому максимальный параллелизм = число партиций (лишние консьюмеры простаивают).

Разные группы читают топик независимо (каждая со своим offset) — так реализуется pub/sub: одно сообщение получают все группы, но внутри группы — только один консьюмер. При изменении состава группы происходит rebalance — перераспределение партиций.

120Какие бывают гарантии доставки (at-most-once / at-least-once / exactly-once)?▶

At-most-once — коммит offset до обработки: при сбое сообщение теряется, но не дублируется. At-least-once — коммит после обработки: при сбое возможен повтор (дубли), но не потеря — самый частый выбор. Exactly-once — каждое сообщение учтено ровно один раз.

Kafka поддерживает EOS для потоков (идемпотентный producer + транзакции read-process-write внутри Kafka). Но для внешних эффектов (запись в чужую БД, отправка письма) настоящий exactly-once недостижим — его эмулируют at-least-once + идемпотентность обработчика.

121Как Kafka обеспечивает порядок сообщений? Какова роль ключа партиционирования?▶

Порядок гарантируется только в пределах одной партиции. Ключ сообщения хэшируется и определяет партицию, поэтому все сообщения с одинаковым ключом (например, orderId) попадают в одну партицию и обрабатываются по порядку.

Следствия: выбирать ключ так, чтобы связанные события шли упорядоченно, но при этом ключи распределялись равномерно (иначе «горячая» партиция). Без ключа сообщения раскидываются равномерно, но межсообщенческого порядка нет. Изменение числа партиций ломает прежнее распределение по ключу.

122Что такое rebalance и какие с ним проблемы?▶

Rebalance — перераспределение партиций между консьюмерами группы при изменении её состава (присоединение/уход/таймаут консьюмера) или числа партиций. Во время stop-the-world rebalance потребление приостанавливается.

Проблемы: паузы и всплески latency, повторная обработка (дубли) при ещё не закоммиченных offset'ах, «rebalance storm» из-за долгой обработки/превышения max.poll.interval или сбоев heartbeat. Митигация: cooperative/incremental rebalancing, static membership, разумные таймауты, быстрая обработка poll-батча, вынос тяжёлой работы из poll-цикла.

123Как обрабатывать «ядовитые» сообщения (dead-letter queue)?▶

Poison message — сообщение, которое стабильно падает при обработке и блокирует прогресс (особенно в упорядоченной партиции). Решение: ограничить число ретраев и после исчерпания отправить сообщение в dead-letter queue/topic с метаданными об ошибке, продолжив обработку остальных.

Дополнительно: ретраи с backoff (retry-топики), мониторинг и алерты на DLQ, инструмент для разбора и переотправки. Важно не «бесконечно ретраить» отравленное сообщение и не терять его молча.

124Что такое retention и log compaction в Kafka?▶

Retention — политика хранения: сообщения удаляются по времени (retention.ms) или по размеру лога, независимо от того, прочитаны ли они (consumer не «забирает» сообщение, как в RabbitMQ).

Log compaction — альтернатива: для каждого ключа хранится хотя бы последнее значение (старые версии того же ключа удаляются). Подходит для топиков-«снимков состояния» (например, последнее состояние сущности по id), позволяя восстановить актуальное состояние реплеем. Можно комбинировать с retention.

125Как устроены exchange, queue и binding в RabbitMQ? Какие типы exchange бывают?▶

Producer публикует в exchange, который по binding'ам и routing key маршрутизирует сообщение в queue(s), откуда читают консьюмеры. Типы exchange: direct (точное совпадение routing key), topic (шаблоны с */#), fanout (всем привязанным очередям, broadcast), headers (по заголовкам).

Это даёт гибкую маршрутизацию: одно сообщение можно разослать в несколько очередей или точечно адресовать. Очереди могут быть durable, с TTL, max-length, DLX (dead-letter exchange).

126Что такое ack/nack и prefetch в RabbitMQ?▶

ack подтверждает успешную обработку — только тогда брокер удаляет сообщение; nack/reject отклоняет (с requeue или в DLX). Без manual ack (auto-ack) сообщение считается доставленным сразу и теряется при сбое консьюмера. Manual ack даёт at-least-once.

prefetch (basicQos) ограничивает число неподтверждённых сообщений на консьюмере — backpressure и равномерное распределение: без него один консьюмер нахватает весь поток, а остальные простаивают. Малый prefetch — честнее распределение, больший — выше throughput.

127Как добиться exactly-once обработки на практике (через идемпотентность)?▶

Полагаются на at-least-once доставку + идемпотентную обработку. Каждое сообщение несёт уникальный id; обработчик в одной транзакции проверяет/записывает этот id в таблицу обработанных и применяет бизнес-эффект (UPSERT, условный апдейт). Повтор того же id — no-op.

Если эффект — публикация дальше, комбинируют с Outbox. Так получают «effectively-once»: инфраструктура может доставить дважды, но наблюдаемый результат — однократный. Чисто инфраструктурный exactly-once без идемпотентности на внешние системы нереализуем.

128Что такое schema registry и зачем он нужен?▶

Schema registry хранит и версионирует схемы сообщений (Avro/Protobuf/JSON Schema). Producer регистрирует/ссылается на схему, в сообщение пишется её id; consumer по id получает схему для десериализации.

Зачем: гарантия совместимости контрактов между сервисами, проверка эволюции схемы (backward/forward compatibility) при публикации — нельзя выкатить ломающее изменение, компактность (не возить схему в каждом сообщении). Это центральный контроль над контрактами в event-driven системе.

129Что делает API RESTful? Что такое уровни зрелости Ричардсона?▶

REST — архитектурный стиль: ресурсы с URI, единообразный интерфейс через HTTP-методы, stateless-взаимодействие, представления (JSON), использование статусов и кэширования. Сервер не хранит сессию между запросами.

Модель зрелости Ричардсона: L0 — один endpoint/RPC поверх HTTP; L1 — ресурсы (отдельные URI); L2 — правильные HTTP-методы и статус-коды (большинство «REST» API здесь); L3 — HATEOAS (гипермедиа-ссылки на доступные действия). Полный REST — L3, но на практике обычно достаточно L2.

130Чем отличаются PUT, POST и PATCH? Какие HTTP-методы идемпотентны?▶

POST — создать/выполнить действие, не идемпотентен (повтор создаёт дубль). PUT — полная замена ресурса по известному URI, идемпотентен (повтор даёт тот же результат). PATCH — частичное обновление; идемпотентность зависит от семантики (JSON Merge Patch обычно идемпотентен, операции вроде «увеличить» — нет).

Идемпотентны: GET, PUT, DELETE, HEAD, OPTIONS. Не идемпотентен: POST (и PATCH в общем случае). GET/HEAD к тому же безопасны (без побочных эффектов). Это важно для ретраев: безопасно повторять только идемпотентные.

131Как версионировать REST API?▶

Способы: в URL (/api/v1/...) — просто и явно, самый распространённый; в заголовке (Accept: application/vnd.app.v2+json, content negotiation) — чище URI, но менее прозрачно; в query (?api-version=2).

Принципы: предпочитать обратно совместимые изменения (аддитивные поля) и не плодить версии без нужды; при breaking change — новая версия с переходным периодом, депрекейт-заголовки, поддержка N и N-1, миграция клиентов, затем вывод старой. В .NET — пакет Asp.Versioning.

132Что такое идемпотентность запроса и idempotency key?▶

Идемпотентность — повтор запроса не создаёт дополнительного эффекта. POST по природе не идемпотентен, но на ненадёжной сети клиент может повторить «создание платежа» и задвоить его.

Idempotency key — уникальный ключ, который клиент шлёт в заголовке; сервер запоминает результат первого запроса с этим ключом и на повторы возвращает тот же ответ, не выполняя операцию заново. Так платёжные API защищаются от дублей при ретраях. Ключ + результат хранят с TTL, запись — атомарно с эффектом.

133Как проектировать пагинацию (offset против cursor)?▶

Offset/limit (?page=3&size=20) — прост, позволяет прыгать на страницу, но на больших смещениях медленный (OFFSET сканирует пропускаемые строки) и нестабилен при вставках/удалениях (сдвиг, дубли/пропуски).

Cursor/keyset (WHERE id > lastId ORDER BY id LIMIT n) — стабильный и быстрый на больших объёмах (использует индекс), идеален для бесконечной ленты и реального времени, но нельзя прыгнуть на произвольную страницу. Для лент/больших данных — cursor; для админок с нумерацией страниц — offset.

134Что такое gRPC и на чём он основан (HTTP/2, protobuf)?▶

gRPC — RPC-фреймворк: вызываешь удалённый метод как локальный. Транспорт — HTTP/2 (мультиплексирование, бинарные фреймы, header compression, streaming), сериализация — Protocol Buffers (компактный бинарный формат со схемой .proto, из которой генерируются клиент и сервер).

Плюсы: компактность и скорость, строгий контракт, кодогенерация, двунаправленный стриминг, мультиязычность. Хорош для внутренней межсервисной коммуникации с высоким throughput и низкой latency.

135Какие типы вызовов есть в gRPC (unary, server/client/bidirectional streaming)?▶

Unary — классический запрос-ответ (один к одному). Server streaming — один запрос, поток ответов (подписки, выгрузка большого результата). Client streaming — поток запросов, один ответ (загрузка, агрегация). Bidirectional streaming — оба стороны шлют потоки независимо (чат, реальное время).

Стриминг — естественное следствие HTTP/2 и ключевое преимущество gRPC над обычным REST для потоковых сценариев.

136Когда gRPC лучше REST, а когда хуже?▶

gRPC лучше: внутренняя межсервисная связь, высокий throughput/низкая latency, строгие контракты и кодогенерация, стриминг, полиглот-окружение. REST/JSON лучше: публичные API, браузерные клиенты (gRPC-Web нужен прокси), простота отладки (human-readable, curl), широкая совместимость, кэширование на HTTP-уровне.

Бинарность protobuf даёт скорость, но снижает читаемость и усложняет отладку/совместимость с инструментами. Частый паттерн: gRPC внутри, REST на внешнем шлюзе.

137Как версионировать protobuf-контракты без потери совместимости?▶

Правила protobuf для совместимости: не менять номера полей (wire-идентификатор), не переиспользовать номера удалённых полей (помечать reserved), не менять тип поля, новые поля делать опциональными с дефолтами. Тогда старые и новые клиенты/серверы понимают друг друга (forward/backward compatible).

Удалять поля — через reserved; переименование безопасно (имя не на проводе, важен номер). Крупные несовместимые изменения — новый сервис/пакет с новой версией. Совместимость проверяют схемными линтерами (buf) и contract-тестами.

138Что такое deadline и cancellation в gRPC?▶

Deadline — абсолютный срок выполнения вызова, который клиент задаёт и который распространяется по цепочке вызовов: сервер видит оставшееся время и может прекратить работу, не тратя ресурсы на заведомо просроченный запрос. Лучше относительного timeout, т.к. учитывает уже потраченное время.

Cancellation — клиент может отменить вызов (или соединение оборвалось); сервер получает CancellationToken и прекращает обработку. Вместе они предотвращают накопление «зависших» вызовов и каскадные отказы. Всегда задавать deadline и пробрасывать токен.

139Как обрабатывать ошибки в gRPC (status codes)?▶

gRPC использует свои status codes (OK, INVALID_ARGUMENT, NOT_FOUND, ALREADY_EXISTS, PERMISSION_DENIED, UNAUTHENTICATED, DEADLINE_EXCEEDED, UNAVAILABLE, INTERNAL и др.) — это не HTTP-коды. Сервер бросает RpcException с кодом и сообщением.

Для деталей — rich error model (google.rpc.Status с подробностями, например список нарушенных полей). Клиент решает по коду, ретраить ли (UNAVAILABLE — да, INVALID_ARGUMENT — нет). Важно не утекать внутренние детали в INTERNAL.

140Что такое rate limiting и как его реализовать?▶

Rate limiting ограничивает число запросов (на клиента/ключ/IP) для защиты от перегрузки и злоупотреблений. Алгоритмы: token bucket (пополняемые токены, допускает всплески), leaky bucket, fixed window (просто, но всплеск на границе окна), sliding window (точнее).

В ASP.NET Core 7+ есть встроенный RateLimiter middleware с этими политиками. Для нескольких инстансов состояние счётчиков держат в общем хранилище (Redis). Ответ при превышении — 429 Too Many Requests с заголовком Retry-After. Часто комбинируют с лимитами на шлюзе.

11Кэширование и Redis8 вопросов
📦 пэт-проект: RedisLab
141Какие стратегии кэширования знаешь (cache-aside, write-through, write-behind)?▶

Cache-aside (lazy) — приложение само читает кэш, при промахе грузит из БД и кладёт в кэш; самый частый паттерн. Write-through — запись идёт в кэш и синхронно в БД (кэш всегда консистентен, запись медленнее). Write-behind (write-back) — запись в кэш, в БД асинхронно пачкой (быстрая запись, риск потери при сбое). Read-through — кэш сам подгружает из источника.

Выбор по профилю: read-heavy с допустимой устареваемостью — cache-aside; нужна свежесть — write-through; экстремальная запись — write-behind с осознанием рисков.

142Инвалидация кэша — самое сложное. Как ты её решаешь?▶

Подходы: TTL (просто, данные сами протухают — годится, если допустима небольшая устареваемость), явная инвалидация по событию (при изменении сущности удаляем/обновляем ключ), версионирование ключей (меняем ключ при изменении, старое протухает по TTL), теги для групповой инвалидации.

На практике комбинирую: короткий TTL как страховка + событийная инвалидация для важных данных. Главное — решить допустимую степень устаревания (cache staleness) с бизнесом; стопроцентная мгновенная консистентность кэша дорога и часто не нужна.

143Что такое cache stampede и как с ним бороться?▶

Cache stampede (dogpile) — при истечении/промахе популярного ключа множество запросов одновременно идут в БД за одним и тем же значением, перегружая её. Особенно опасно при одновременном протухании.

Меры: single-flight / locking (только один пересчитывает, остальные ждут результат), early/probabilistic expiration (обновлять до фактического истечения), jitter в TTL (разнести истечения), stale-while-revalidate (отдать устаревшее, пересчитать в фоне). В .NET — HybridCache (.NET 9) с встроенной защитой от stampede.

144Чем in-memory кэш отличается от распределённого (Redis)?▶

In-memory (IMemoryCache) — в памяти процесса: сверхбыстрый, без сериализации/сети, но не разделяется между инстансами (у каждого свой → рассинхрон), теряется при рестарте, ограничен памятью процесса. Распределённый (Redis, IDistributedCache) — общий для всех инстансов, переживает рестарт приложения, масштабируется, но платит сетью и сериализацией.

Часто используют двухуровневый кэш (L1 локальный + L2 Redis) — HybridCache делает это из коробки, сочетая скорость и согласованность.

145Какие структуры данных есть в Redis и для чего они нужны?▶

String (значения, счётчики, кэш), Hash (объект с полями), List (очереди, стеки), Set (уникальные элементы, пересечения), Sorted Set/ZSet (рейтинги, leaderboard'ы, отложенные задачи по score=time), Stream (лог событий, как мини-Kafka), HyperLogLog (приблизительный счёт уникальных), Bitmap, Geo, Pub/Sub.

Богатство структур — ключевое преимущество Redis над «просто кэшем»: rate limiting, сессии, очереди, лидерборды, дедупликация решаются нативно.

146Как реализовать распределённую блокировку на Redis и почему это непросто?▶

Базово: SET lock value NX PX ttl — атомарно захватить, если ключа нет, с TTL. Освобождение — только своим уникальным токеном через Lua-скрипт (проверка значения + DEL атомарно), иначе можно снять чужой лок.

Непросто из-за: истечения TTL до завершения работы (другой захватит лок, пока первый ещё работает → нужен fencing token), сбоев и failover мастера (Redlock на N узлах спорен по корректности — критика Kleppmann'а), часового дрейфа. Вывод: для строгих гарантий Redis-лок недостаточен — нужен fencing или consensus-стор (etcd/ZooKeeper); для «best-effort» взаимоисключения подходит.

147Что такое TTL и какие бывают политики вытеснения (eviction)?▶

TTL — время жизни ключа, после которого он удаляется (expiration). Когда память заполнена (maxmemory), включается eviction по политике: noeviction (ошибки на запись), allkeys-lru/volatile-lru (вытеснять давно неиспользуемые из всех/только с TTL), allkeys-lfu/volatile-lfu (по частоте использования), volatile-ttl (с ближайшим истечением), random.

Для чистого кэша обычно allkeys-lru/lfu. Для данных, которые нельзя терять (сессии, очереди), вытеснение по ключам опасно — их хранят отдельно/с noeviction.

148Какие данные не стоит кэшировать?▶

Не стоит: данные, требующие строгой свежести и где устаревание недопустимо (баланс, остатки склада при списании), персональные/чувствительные данные без шифрования и контроля доступа, редко читаемые (низкий hit rate — кэш не окупается), быстро меняющиеся (инвалидация дороже выгоды), и результаты, зависящие от множества меняющихся факторов (низкая переиспользуемость ключа).

Кэш окупается на read-heavy, относительно стабильных, дорого-вычисляемых данных. Перед кэшированием — измерить hit rate и допустимую staleness; иначе кэш добавит сложность и баги без выигрыша.

12Контейнеры, Kubernetes, CI/CD12 вопросов
📦 пэт-проект: K8sLab
149Как уменьшить размер Docker-образа (multi-stage build)?▶

Multi-stage build: один stage с SDK собирает приложение, финальный — копирует только результат (dotnet publish) в лёгкий runtime-образ (aspnet/runtime), без SDK и исходников. Это резко уменьшает размер и поверхность атаки.

Ещё: базовые образы alpine/chiseled (минимальные), Native AOT (нет рантайма), .dockerignore (не тащить мусор), объединение слоёв, удаление кэшей пакетов, non-root пользователь. Меньше образ → быстрее pull/деплой и меньше уязвимостей.

150Чем ENTRYPOINT отличается от CMD? Что такое слои образа?▶

ENTRYPOINT задаёт исполняемый процесс контейнера (что запускать всегда), CMD — аргументы по умолчанию (легко переопределяются при docker run). Часто ENTRYPOINT — само приложение, CMD — параметры. Если задан только CMD, он и есть команда запуска.

Слои — каждая инструкция Dockerfile (RUN/COPY/ADD) создаёт неизменяемый слой; образ — стек слоёв с кэшированием. Порядок важен: редко меняющееся (восстановление зависимостей) — раньше, часто меняющийся код — позже, чтобы максимизировать переиспользование кэша при сборке.

151Что такое Deployment, Service и Ingress в Kubernetes?▶

Deployment управляет набором подов через ReplicaSet: задаёт число реплик, образ, стратегию обновления (rolling), самовосстановление. Service — стабильная сетевая точка (виртуальный IP + DNS) и балансировка на эфемерные поды (по label selector); типы ClusterIP/NodePort/LoadBalancer. Ingress — L7-маршрутизация HTTP(S) снаружи в сервисы (хосты/пути, TLS) через ingress-контроллер (Nginx, Traefik).

Цепочка: внешний трафик → Ingress → Service → Pods (Deployment их поддерживает в нужном количестве).

152Что такое liveness и readiness probe и зачем нужны обе?▶

Liveness — «жив ли процесс»; при провале Kubernetes перезапускает под (лечит зависшие/дедлокнутые приложения). Readiness — «готов ли принимать трафик»; при провале под выводится из Service (трафик не идёт), но не перезапускается.

Нужны обе: readiness — для прогрева, ожидания зависимостей и graceful shutdown (увести трафик до остановки); liveness — для восстановления реально сломанных. Также startup probe для медленного старта. Ошибка — вешать на liveness тяжёлые проверки зависимостей: упавшая БД вызовет бесконечные рестарты.

153Как настроить автоскейлинг (HPA) и по каким метрикам?▶

HPA (Horizontal Pod Autoscaler) меняет число реплик Deployment по метрикам: базово CPU/memory, но лучше — по нагрузочным (RPS, длина очереди, p95 latency) через custom/external metrics (Prometheus Adapter, KEDA для event-driven скейла по Kafka/RabbitMQ/Redis).

Настройка: целевое значение метрики, min/max реплик, поведение стабилизации (anti-flapping). Для корректной работы у подов должны быть выставлены requests. Дополняется VPA (вертикально) и Cluster Autoscaler (добавляет ноды). Метрику выбирают ту, что реально отражает нагрузку сервиса.

154Что такое requests и limits ресурсов? Что произойдёт при их превышении?▶

Requests — гарантированный минимум, по нему планировщик размещает под на ноду и считает HPA. Limits — потолок потребления. Превышение по CPU — троттлинг (под не убивают, но он замедляется). Превышение по памяти сверх limit — под убивается с OOMKilled.

Соотношение request/limit задаёт QoS-класс (Guaranteed/Burstable/BestEffort), влияющий на приоритет вытеснения при нехватке ресурсов на ноде. Практика: ставить реалистичные requests (по факту нагрузки) и аккуратные limits, особенно по памяти; для .NET учитывать, что GC видит лимиты контейнера.

155Как управлять конфигами и секретами (ConfigMap, Secret)?▶

ConfigMap — несекретная конфигурация (переменные окружения, файлы), Secret — чувствительные данные (base64, не шифрование!). Подключаются как env-переменные или примонтированные файлы. Это отделяет конфигурацию от образа (один образ — разные окружения).

Секреты по-настоящему защищают: шифрование etcd at-rest, RBAC на доступ, внешние стора (Vault, cloud KMS) через CSI Secrets Store, sealed-secrets для git. Нельзя класть секреты в образ/git в открытом виде. Изменение ConfigMap/Secret обычно требует перезапуска подов (если не настроен hot-reload/reloader).

156Что такое Helm и зачем он нужен?▶

Helm — пакетный менеджер Kubernetes: chart — шаблонизированный набор манифестов с values.yaml для параметризации. Решает дублирование YAML между окружениями (dev/stage/prod — одни шаблоны, разные values), версионирование релизов, установку/обновление/откат одной командой (helm upgrade/rollback).

Альтернативы/дополнения: Kustomize (overlay без шаблонов), GitOps (Argo CD/Flux). Helm удобен для переиспользуемых пакетов и сторонних приложений; для своих сервисов многие предпочитают Kustomize за простоту.

157Опиши устройство типичного CI/CD пайплайна на твоём примере.▶

CI: на push/PR — restore, build, unit + integration тесты (Testcontainers), статанализ/линт, security scan (зависимости, образ), сборка Docker-образа, тег по commit SHA, публикация в registry. PR не мержится без зелёного пайплайна.

CD: деплой в staging (автоматически), миграции БД отдельным шагом, smoke-тесты; в prod — по аппруву, стратегией rolling/canary, с health-check'ами и автоматическим откатом при провале. GitOps-подход: желаемое состояние в git, Argo CD синхронизирует кластер. Ключевое — повторяемость, тесты как гейт, быстрый и безопасный rollback.

158Какие стратегии деплоя знаешь (blue-green, canary, rolling)?▶

Rolling — постепенная замена старых подов новыми (дефолт в k8s): без простоя, но обе версии какое-то время сосуществуют (нужна совместимость). Blue-green — две полные среды, переключение трафика разом на новую; мгновенный откат, но двойные ресурсы. Canary — новая версия получает малую долю трафика, при здоровых метриках — постепенное увеличение; раннее обнаружение проблем на малой аудитории.

Выбор: повседневно — rolling/canary; критичные релизы с быстрым откатом — blue-green. Все требуют обратной совместимости схемы БД (expand/contract).

159Как организовать безопасный откат (rollback)?▶

Откат должен быть быстрым и предсказуемым: версионированные иммутабельные образы (тег по SHA) и манифесты в git → kubectl rollout undo/helm rollback/перевод GitOps на предыдущий коммит. Health-check'и и метрики триггерят автоматический откат при провале выкатки.

Главная сложность — миграции БД: схема должна быть совместима со старой и новой версией кода (expand/contract), чтобы откат кода не требовал отката БД (откат данных опасен). Откат регулярно репетируют; feature flags позволяют «откатить» поведение без передеплоя.

160Под падает с OOMKilled — как ты будешь это диагностировать?▶

OOMKilled = превышен memory limit. Шаги: kubectl describe pod (reason, exit 137, рестарты), метрики памяти (Grafana/metrics-server) — это всплеск или плавный рост (утечка)? Сопоставить с нагрузкой/релизом.

Дальше: профилирование памяти .NET (dotnet-counters/dotnet-gcdump, dotMemory) — большие аллокации, LOH-фрагментация, незакрытые ресурсы, кэш без лимита. Решения: поднять limit (если просто мало), починить утечку/аллокации, ограничить кэш, настроить GC под контейнер. Важно: лимиты контейнера видны .NET GC, и слишком низкий limit при больших Gen0/LOH провоцирует OOM.

13Тестирование10 вопросов
📦 пэт-проект: TestingLab
161Опиши тест-пирамиду. Каких тестов должно быть больше всего?▶

Пирамида: основание — много быстрых unit-тестов (изолированные, миллисекунды), середина — меньше интеграционных (с БД/брокером/HTTP), вершина — мало медленных e2e/UI. Чем выше — тем дороже, медленнее и хрупче.

Больше всего — unit; они дают быструю обратную связь и стабильность. Антипаттерны: «мороженое» (много e2e, мало unit — медленно и флаки) и «песочные часы» (мало интеграционных при микросервисах). Современный взгляд (testing trophy) поднимает долю интеграционных, т.к. они проверяют реальное взаимодействие. Главное — баланс по скорости/уверенности.

162Что и зачем мокать? Когда обилие моков — это запах кода?▶

Мокать стоит внешние зависимости с побочными эффектами и недетерминизмом: сеть, БД, время, очереди, сторонние API — чтобы тест был быстрым, детерминированным и проверял логику в изоляции.

Обилие моков — запах: если для теста нужно настроить 5+ моков, класс делает слишком много (нарушение SRP) или высокая связность/leaky-абстракции. Также мок собственного кода вместо реального ведёт к тестам, проверяющим взаимодействие, а не поведение (хрупко при рефакторинге). Тренд — мокать только границы системы, внутреннее тестировать с реальными объектами (или Testcontainers для БД).

163Чем интеграционный тест отличается от юнита?▶

Unit проверяет одну единицу (класс/метод) в изоляции, без I/O, быстро и детерминированно; зависимости подменены. Интеграционный проверяет совместную работу нескольких компонентов с реальной инфраструктурой (БД, HTTP, брокер) — например, репозиторий против настоящей PostgreSQL в Testcontainers или endpoint через WebApplicationFactory.

Unit ловит логические ошибки дёшево; интеграционные ловят то, что unit не видит: SQL/маппинг, конфигурацию, сериализацию, контракты. Нужны оба уровня.

164Что такое Testcontainers и зачем они нужны?▶

Testcontainers поднимают реальные зависимости (PostgreSQL, Redis, Kafka, RabbitMQ) в Docker-контейнерах прямо из теста, с автоматическим запуском и очисткой. Тест работает против настоящей БД, а не in-memory заглушки.

Зачем: in-memory провайдеры EF не воспроизводят реальный SQL/поведение БД (другой диалект, отсутствие констрейнтов), что даёт ложную уверенность. Testcontainers дают высокую достоверность интеграционных тестов при изоляции и повторяемости. Минус — нужен Docker и тесты медленнее unit. Идеальны для проверки слоя данных и end-to-end внутри сервиса.

165Как тестировать асинхронный код?▶

Тест делают async Task и await'ят проверяемый код (не блокировать .Result). Проверка исключений — await Assert.ThrowsAsync<T>. Для отмены — передать сработавший CancellationToken и проверить OperationCanceledException.

Сложное — недетерминизм и время: использовать TimeProvider/FakeTimeProvider вместо реальных задержек (не Task.Delay в тестах), детерминированно управлять порядком через TaskCompletionSource, тестировать конкурентность нагрузкой/повторами. Избегать произвольных sleep для «ожидания» — источник флаки-тестов.

166Что такое контрактные тесты для микросервисов?▶

Contract testing проверяет совместимость API между потребителем и поставщиком без поднятия обоих в e2e. Consumer-driven contracts (Pact): потребитель описывает ожидания (запрос→ответ), генерируется контракт, поставщик прогоняет его у себя и подтверждает, что не сломал ожидания.

Зачем: e2e-тесты всех сервисов медленны и хрупки; контрактные ловят несовместимости контрактов рано и независимо, в CI каждого сервиса. Так безопасно эволюционировать API без страха сломать потребителей.

167Что делает код тестируемым, а что мешает тестируемости?▶

Тестируемость дают: инверсия зависимостей (DI вместо new), чистые функции и детерминизм, малые классы с одной ответственностью, явные зависимости в конструкторе, абстракция I/O и времени за интерфейсами.

Мешают: статика и синглтоны (DateTime.Now, static-хелперы, service locator), скрытое создание зависимостей внутри (new HttpClient()), глобальное состояние, большие методы с множеством веток и побочных эффектов, тесная связность. Если тест писать тяжело — обычно это сигнал плохого дизайна, а не «неудобного тестирования».

168Что такое TDD и где он уместен?▶

TDD — цикл red-green-refactor: сначала падающий тест на требуемое поведение, затем минимальный код, чтобы он прошёл, затем рефакторинг. Тесты ведут дизайн и дают защитную сетку.

Уместен там, где требования и поведение понятны и важна корректность: доменная логика, алгоритмы, баг-фиксы (сначала тест, воспроизводящий баг), API с чёткими контрактами. Менее удобен в исследовательском/UI/прототипном коде, где дизайн ещё не ясен. TDD — инструмент, а не догма; ценность — в тестируемом дизайне и быстрой обратной связи, а не в ритуале.

169Как тестировать код, зависящий от времени (DateTime.Now)?▶

Прямой DateTime.Now/UtcNow делает код недетерминированным. Решение — абстрагировать время: в .NET 8+ внедрять TimeProvider (в тестах — FakeTimeProvider, можно «прокручивать» время), раньше — свой IClock/IDateTimeProvider.

Тогда тест задаёт фиксированное «сейчас», проверяет логику дедлайнов/TTL/расписаний детерминированно и без реальных задержек. То же для таймеров/задержек — управляемый TimeProvider вместо Task.Delay. Это убирает целый класс флаки-тестов.

170Что такое flaky-тесты и как с ними бороться?▶

Flaky-тест проходит/падает недетерминированно без изменения кода. Подрывает доверие к набору (люди перезапускают и игнорируют падения). Причины: зависимость от времени/таймаутов/sleep, порядка тестов и общего состояния, реальной сети, гонок, недетерминированных данных (текущая дата, random, культура).

Борьба: изолировать тесты (чистое состояние, без общих ресурсов), управляемое время (TimeProvider), ждать условие, а не фиксированную задержку, детерминировать данные, чинить гонки. Флаки нужно лечить, а не маскировать ретраями; в крайнем случае — карантин с обязательным заведением задачи на фикс.

14Производительность и highload10 вопросов
📦 пэт-проект: PerfLab
171Опиши свой пошаговый подход к диагностике медленного эндпоинта.▶

1) Измерить, а не гадать: метрики/трейсы (APM, OpenTelemetry) — где время: БД, внешний вызов, сериализация, CPU, ожидание пула. 2) Воспроизвести под нагрузкой, смотреть p95/p99, а не среднее. 3) Локализовать узкое место по распределённому трейсу (span'ы).

4) Если БД — план запроса, N+1, индексы. Если CPU/аллокации — профайлер (dotTrace/PerfView). Если ожидание — пул потоков/соединений, блокировки. 5) Исправить корневую причину, повторно замерить. Оптимизировать по данным профилирования, а не по интуиции; сначала самый дорогой участок.

172Что такое BenchmarkDotNet и как корректно измерять производительность?▶

BenchmarkDotNet — стандарт микробенчмаркинга в .NET: прогревает JIT, делает множество итераций, считает статистику (среднее, медиана, разброс), учитывает аллокации ([MemoryDiagnoser]), сравнивает варианты.

Корректность: не мерить вручную Stopwatch (без прогрева и в Debug — мусор), измерять в Release без отладчика, избегать dead-code elimination (возвращать результат), репрезентативные данные, не путать микробенчмарк с реальной нагрузкой. Микробенчмарки — для горячих участков; для системы — нагрузочное тестирование.

173Какие инструменты профилирования .NET знаешь (dotTrace, dotMemory, PerfView)?▶

CPU/время: dotTrace, PerfView, Visual Studio Profiler, dotnet-trace — где тратится время, горячие методы, дерево вызовов. Память: dotMemory, dotnet-gcdump, PerfView — кто держит память, утечки, фрагментация LOH, нагрузка на GC. Лайв-метрики: dotnet-counters (GC, ThreadPool, экзепшены, RPS), dotnet-dump для анализа дампов.

Кросс-платформенные dotnet-* tools удобны на проде/в контейнерах. Выбор инструмента — по гипотезе: CPU-bound, память или contention.

174Как найти и устранить утечку памяти в .NET?▶

Симптом — память растёт и не возвращается. Снять несколько gcdump/snapshot'ов с интервалом, сравнить (diff) — какие типы растут. Найти GC roots, удерживающие объекты.

Типичные причины в .NET: неотписанные обработчики событий (издатель держит подписчиков), статические коллекции/кэши без лимита и TTL, захват this в долгоживущих делегатах, незаосвобождённые IDisposable, HttpClient-антипаттерны, удержание больших объектов. Устранение: отписка, ограничение кэшей, корректный Dispose, разрыв удерживающих ссылок. После фикса — проверить, что память стабилизируется под нагрузкой.

175Что чаще всего тормозит backend под нагрузкой?▶

Чаще всего — база данных: неоптимальные запросы, отсутствие индексов, N+1, блокировки, исчерпание connection pool. Затем — блокирующий I/O в async (.Result/.Wait()) и thread pool starvation, чрезмерные аллокации и давление на GC, синхронные внешние вызовы без таймаутов/кэша, и contention на блокировках/общих ресурсах.

Реже — сериализация, логирование в горячем пути, неэффективные алгоритмы. Порядок проверки обычно: БД → пулы/блокировки → аллокации/GC → внешние зависимости. Конкретику даёт профилирование, а не догадки.

176Как уменьшить количество аллокаций в горячем пути?▶

Приёмы: Span<T>/stackalloc вместо временных массивов, ArrayPool<T>/ObjectPool для переиспользования буферов, StringBuilder/string.Create вместо конкатенации, избегать LINQ в горячем цикле (он аллоцирует итераторы/замыкания), кэшировать делегаты, struct для мелких значений, ValueTask при частом синхронном результате.

Ещё: избегать boxing (дженерики, IEquatable), не логировать с интерполяцией в hot path (structured logging с шаблоном), системные API на спанах (Utf8Formatter, Utf8JsonReader). Меньше аллокаций → реже GC → стабильнее latency/p99. Мерить через MemoryDiagnoser.

177Горизонтальное против вертикального масштабирования — что выберешь и почему?▶

Вертикальное (мощнее машина) — просто, без изменений в коде, но есть потолок, единая точка отказа и дорого на пике. Горизонтальное (больше инстансов) — эластично, отказоустойчиво, почти без потолка, но требует stateless-сервисов, балансировки и распределённого состояния (БД/кэш становятся узким местом).

В облаке/highload предпочитают горизонтальное (автоскейл, устойчивость). Вертикальное — как быстрый временный буст или для компонентов, плохо масштабируемых горизонтально (некоторые БД). Часто комбинируют: горизонтально — stateless сервисы, вертикально/шардинг — хранилище.

178Что такое stateless-сервис и почему это важно для масштабирования?▶

Stateless-сервис не хранит состояние между запросами в памяти инстанса: любой инстанс может обработать любой запрос, состояние вынесено в БД/Redis/токен. Сессионная привязка (sticky) не нужна.

Важно для горизонтального масштабирования: можно свободно добавлять/убирать инстансы, балансировать без привязки, переживать падения подов без потери данных, делать rolling-деплой. In-memory состояние (локальные сессии, кэш-только-здесь) ломает это — после рестарта/скейла данные теряются или расходятся. Поэтому состояние выносят во внешние общие сторы.

179Как провести нагрузочное тестирование (k6 / NBomber)? Что такое p95/p99?▶

Определить цель (целевой RPS, SLO по latency), сценарии (реалистичные пользовательские пути и данные), окружение, близкое к проду. Инструменты: k6 (скрипты на JS), NBomber (.NET), JMeter/Gatling. Виды: load (ожидаемая нагрузка), stress (до отказа — найти предел), soak (длительный — утечки), spike.

p95/p99 — перцентили: p99 = 200 мс значит, что 99% запросов быстрее 200 мс. Среднее обманчиво (маскирует хвосты), поэтому SLO задают по перцентилям — именно хвостовая latency определяет реальный опыт под нагрузкой. Смотрят latency vs throughput и точку деградации.

180Расскажи про оптимизацию, которой гордишься, с метриками до и после.▶

Структура (с цифрами): проблема (например, эндпоинт p99 = 1.5 с под нагрузкой, периодические таймауты), диагностика (трейс показал N+1 и отсутствие индекса → 300+ запросов к БД на запрос), решение (проекция в DTO одним запросом + составной covering-индекс + кэш справочника).

Результат в метриках: p99 1.5 с → 90 мс, число SQL-запросов 300 → 3, нагрузка на БД −70%, throughput ×4. Подчеркни подход: измерил → нашёл корневую причину → точечно исправил → подтвердил замерами и нагрузочным тестом, а не «оптимизировал всё подряд».

15Наблюдаемость и эксплуатация6 вопросов
📦 пэт-проект: ObservabilityLab
181Три столпа observability — логи, метрики, трейсы. Чем они отличаются?▶

Логи — дискретные события с контекстом («что произошло»), хороши для деталей и расследования конкретного случая. Метрики — числовые агрегаты во времени (RPS, latency, ошибки, CPU), дёшевы в хранении, основа дашбордов и алертов («что-то не так и насколько»). Трейсы — путь одного запроса через сервисы со span'ами и таймингами («где именно медленно/сломалось»).

Они дополняют друг друга: метрика сигналит о проблеме → трейс локализует сервис/шаг → лог даёт детали. Связываются через trace/correlation id.

182Что такое OpenTelemetry?▶

OpenTelemetry (OTel) — вендоронезависимый стандарт и SDK для сбора телеметрии (трейсы, метрики, логи) с единым API и форматом (OTLP). Инструментируешь код один раз, а экспортировать можно в любой бэкенд (Jaeger, Prometheus, Grafana, Tempo, коммерческие APM) — без привязки к вендору.

В .NET интегрирован нативно: трейсинг через Activity/ActivitySource, метрики через Meter, автоинструментирование ASP.NET Core/HttpClient/EF/брокеров. Это де-факто стандарт observability, заменяющий проприетарные агенты.

183Что такое структурированное логирование (Serilog) и зачем нужен correlation id?▶

Структурированное логирование пишет логи как данные с именованными полями (logger.LogInformation("Order {OrderId} paid {Amount}", id, amt)), а не плоский текст. Поля индексируются → можно фильтровать/агрегировать/строить запросы (в Seq/ELK/Loki). Serilog/ILogger с message template — стандарт в .NET.

Correlation id (trace id) — общий идентификатор запроса, протянутый через все сервисы и попадающий в каждую лог-запись. Без него в распределённой системе невозможно собрать все логи одного запроса. Добавляют через middleware/LogContext/scope, синхронизируют с trace id из OTel.

184Какие метрики ты бы мониторил для backend-сервиса (RED / USE)?▶

RED (для сервисов/запросов): Rate (RPS), Errors (доля ошибок), Duration (latency, перцентили p95/p99). USE (для ресурсов): Utilization, Saturation (очереди, насыщение), Errors — для CPU, памяти, диска, пулов.

Плюс прикладные/инфраструктурные: длина очередей и lag консьюмеров, размер/исчерпание connection pool, GC (паузы, частота, heap), ThreadPool queue, состояние зависимостей (circuit breaker). Алерты — на симптомы, ощущаемые пользователем (latency/error budget по SLO), а не на каждый ресурс.

185Что такое SLI, SLO и SLA?▶

SLI (indicator) — измеряемый показатель качества (доля успешных запросов, доля запросов быстрее 200 мс). SLO (objective) — внутренняя цель по SLI (99.9% успешных за месяц). SLA (agreement) — внешний контракт с клиентом с последствиями (компенсации) при нарушении; обычно мягче SLO.

Из SLO выводят error budget (допустимая доля сбоев): пока бюджет есть — катим фичи быстрее; исчерпан — приоритет на надёжность. Это инструмент баланса между скоростью разработки и стабильностью, основа SRE.

186Как ты подходишь к расследованию инцидента на проде?▶

1) Сначала стабилизировать (mitigate), а не искать корневую причину: откат релиза, переключение трафика, масштабирование, отключение фичи флагом — вернуть сервис пользователям. 2) Оценить масштаб по дашбордам (что задето, с какого момента, корреляция с деплоем/изменением).

3) Локализовать по метрикам→трейсам→логам и trace id. 4) Применить фикс, подтвердить восстановление по метрикам. 5) Постмортем без обвинений (blameless): таймлайн, корневая причина, что починить, чтобы не повторилось (алерты, тесты, защита). Коммуникация со стейкхолдерами по ходу. Цель — быстро восстановить и системно учиться.

16System design (открытые задачи)6 вопросов
📄 статья: SystemDesign
187Спроектируй платёжный шлюз с гарантией отсутствия двойных списаний.▶

Ключ — идемпотентность: клиент шлёт Idempotency-Key на каждую попытку оплаты; сервер хранит ключ+результат и на повтор возвращает прежний ответ, не списывая снова. Запись ключа и эффекта — в одной транзакции.

Состояние платежа — конечный автомат (Pending→Authorized→Captured/Failed) с оптимистичной блокировкой/версией, чтобы исключить гонки. Взаимодействие с провайдером оборачивается ретраями с тем же идемпотентным ключом провайдера. Надёжная интеграция событий — через Outbox; асинхронные результаты от банка (вебхуки) тоже обрабатываются идемпотентно. Аудит каждой операции, reconciliation-сверка с провайдером, таймауты и компенсации (Saga) для зависших авторизаций.

188Спроектируй сервис сокращения ссылок (URL shortener) под высокую нагрузку.▶

Генерация кода: счётчик/Snowflake → base62, либо хэш с проверкой коллизий; предгенерация диапазонов id на инстанс, чтобы не ходить за каждым. Хранилище — key-value (short→long) с шардингом/репликацией; запись редка, чтение огромно (read-heavy).

Чтение: агрессивный кэш (Redis) перед БД, CDN/edge для редиректов, 301/302 с учётом аналитики. Масштабирование горизонтальное (stateless). Доп.: кастомные алиасы, TTL/expiry, защита от абуза (rate limit, проверка вредоносных URL), аналитика кликов асинхронно через очередь (не блокировать редирект). Оценить нагрузку (QPS, объём) и заложить запас.

189Спроектируй систему уведомлений (email/push/SMS) с ретраями и дедупликацией.▶

Приём запросов в очередь (Kafka/RabbitMQ) → воркеры по каналам. Каждый канал — отдельный провайдер за абстракцией (INotificationChannel), выбор стратегией. Дедупликация: идемпотентный ключ уведомления (по событию+получателю+каналу) в processed-таблице, чтобы не слать дубль при повторе сообщения.

Ретраи с экспоненциальным backoff и DLQ для безнадёжных; circuit breaker на падающего провайдера; fallback на резервного. Шаблоны и локализация, пользовательские настройки/частотные лимиты (rate limiting, quiet hours), приоритеты. Статусы доставки от провайдеров — асинхронно (вебхуки) идемпотентно. Outbox для надёжной публикации из основного сервиса. Наблюдаемость: метрики доставки/ошибок по каналам.

190Спроектируй ленту (feed) с пагинацией под миллионы пользователей.▶

Две модели: fan-out on write (push) — при публикации раскидываем в предрассчитанные ленты подписчиков (быстрое чтение, дорогая запись, проблема «звёзд» с миллионами подписчиков) и fan-out on read (pull) — собираем ленту в момент запроса (дёшево писать, дорого читать). На практике — гибрид: push для обычных, pull для знаменитостей.

Ленты в Redis (sorted set по времени/score), cursor-пагинация (keyset, не offset) для стабильности и скорости. Кэширование, шардинг по пользователю, асинхронная обработка через очередь, ранжирование отдельным сервисом. AP-выбор (eventual consistency ленты допустима). Заложить горячие ключи и backpressure.

191Спроектируй идемпотентную обработку входящих вебхуков от платёжной системы.▶

Принять быстро: проверить подпись (HMAC) для аутентичности, сразу вернуть 200 и положить событие в очередь/БД — не обрабатывать синхронно (провайдер ретраит при таймауте). Идемпотентность: у вебхука есть event id; в одной транзакции проверяем/пишем его в processed-таблицу и применяем эффект — повтор того же id становится no-op.

Учесть: вебхуки приходят не по порядку и с дублями — состояние платежа как конечный автомат с допустимыми переходами (игнорировать устаревшие/неприменимые). Ретраи провайдера + наши ретраи обработки с DLQ. Reconciliation (периодическая сверка) на случай потерянных вебхуков. Логировать raw-пейлоады для разбора.

192Спроектируй систему документооборота с генерацией документов под нагрузкой.▶

Генерация — тяжёлая CPU/IO-операция, поэтому асинхронно: запрос создаёт задачу (статус Pending) и кладёт в очередь, клиенту сразу возвращается id для опроса/вебхука. Пул воркеров (масштабируется по длине очереди через KEDA) рендерит документы (шаблоны → PDF/DOCX), что развязывает пики нагрузки.

Готовые файлы — в объектное хранилище (S3/Blob), в БД — метаданные и ссылки; раздача через pre-signed URL/CDN, не через API. Идемпотентность задач (не сгенерировать дубль при повторе), ретраи с DLQ, кэш одинаковых документов, версионирование шаблонов. Лимиты ресурсов на воркер (генерация прожорлива по памяти), приоритезация очередей, наблюдаемость времени генерации и глубины очереди.

17Поведенческие и лидерские8 вопросов
📄 статья: Behavioral
193Расскажи о самой сложной технической задаче и как ты её решил.▶

Используй формат STAR: Situation (контекст и почему сложно), Task (твоя зона ответственности), Action (что конкретно ты делал — анализ, гипотезы, решения, компромиссы), Result (измеримый итог + что вынес).

Выбирай задачу с реальной технической глубиной (распределённая консистентность, тяжёлая оптимизация, сложная миграция), показывай ход мышления и принятие решений в неопределённости, а не только итог. Подчеркни trade-off'ы, командную работу и измеримый результат. Избегай «мы» там, где был твой вклад.

194Как ты подходишь к код-ревью? Что ищешь в первую очередь?▶

Приоритет: корректность (баги, граничные случаи, гонки, обработка ошибок) и безопасность (инъекции, утечки, авторизация) — в первую очередь. Затем — соответствие требованиям, читаемость, поддерживаемость, тесты, влияние на производительность и архитектурная согласованность.

Стиль ревью: доброжелательно и по существу, различать «must fix» и «nit/предложение», объяснять «почему», задавать вопросы вместо приказов, хвалить хорошее. Мелочи форматирования — на линтер/автоформат, чтобы ревью было о сути. Цель — улучшить код и обучать, а не показать превосходство; маленькие PR ревьюятся качественнее.

195Опиши конфликт в команде по техническому решению — как разрешили?▶

STAR с акцентом на процесс: разногласие (например, монолит против выноса в сервис), как ты выслушал аргументы обеих сторон, перевёл спор из «мнений» в факты и критерии (требования, риски, стоимость, данные/прототип), и пришли к решению.

Покажи зрелость: готовность изменить позицию при сильных аргументах («disagree and commit» — поддержать общее решение, даже если был против), фокус на интересах продукта/команды, а не на эго. Хорошая концовка — решение приняли осознанно, зафиксировали (ADR), и оно сработало/чему научило.

196Как ты обосновываешь бизнесу необходимость рефакторинга или работы с тех-долгом?▶

Говорить на языке бизнеса, а не «код некрасивый»: связать тех-долг с метриками и рисками — скорость доставки фич падает, баги/инциденты растут, время выкатки/онбординга увеличивается, риск отказа под нагрузкой. По возможности — цифры (lead time, частота инцидентов, время на фичу).

Предлагать инкрементально: не «остановить всё на 2 месяца», а «бюджет 15–20% спринта» или рефакторинг попутно с фичами в тех же местах (boy scout rule). Показать ожидаемую отдачу и приоритизировать по риску/стоимости. Тех-долг — это компромисс, осознанно управляемый, а не «переписать всё».

197Как ты вводишь джуна в проект и менторишь его?▶

Онбординг: дать карту системы (архитектура, домен, как запустить), парное программирование, первые задачи — небольшие и завершаемые для быстрых побед, чёткие критерии готовности. Доступная документация и «спрашивай не стесняясь».

Менторство: давать задачи на вырост с поддержкой, ревью с объяснением «почему» (учить, а не только указывать), направлять вопросами, чтобы джун думал сам, а не давать готовый ответ. Регулярная обратная связь в обе стороны, хвалить прогресс, постепенно повышать самостоятельность и доверие. Цель — растить инженера, а не исполнителя.

198Расскажи про решение, которое оказалось ошибочным. Какой вывод сделал?▶

Покажи рефлексию и ответственность: конкретное решение (преждевременная оптимизация/микросервисы, неверная технология, недооценённый риск), как обнаружил ошибку (метрики, инцидент, обратная связь), что предпринял, чтобы исправить, и какой системный вывод сделал (что изменил в подходе).

Важно брать ответственность («я решил…», а не «так получилось»), без оправданий, и показать, что ошибка изменила твою практику (например, теперь принимаю решения на данных/прототипе, документирую trade-off'ы в ADR, начинаю с простого). Зрелость = умение признавать и учиться, а не безошибочность.

199Как ты оцениваешь сроки и что делаешь при риске их сорвать?▶

Оценка: декомпозиция на мелкие задачи, оценка диапазоном/с учётом неопределённости (а не одной цифрой), закладывание буфера на неизвестное, учёт зависимостей, тестов и ревью, опора на исторические данные. Озвучивать допущения и риски явно.

При риске срыва — как можно раньше поднять флаг (не молчать до дедлайна), показать прозрачно статус и причины, и предложить варианты: сократить scope/приоритеты, добавить ресурсы, сдвинуть срок, или снизить качество осознанно.
