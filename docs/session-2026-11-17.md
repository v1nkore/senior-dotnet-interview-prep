## Что проверено

- SQL: повторная задача на всех клиентов и сумму оплаченных заказов решена после двух локальных исправлений: сначала `Order` вместо `Orders` и неоднозначный `Id`; затем запрос корректен. Это улучшение относительно 16 ноября, но не чистое решение с первой сдачи.
- Код: вторая задача под заявленным лимитом 10 минут — длина самой длинной подстроки без повторов. Несколько вариантов с `HashSet` не проходили случаи `"abc"` и `"dvdf"`; итоговый алгоритм показан ассистентом. Пользователь разобрал амортизированную сложность после объяснения. Код пользователя не компилировался и не тестировался как готовое решение. Всего в цикле две timed-попытки, ноль самостоятельных корректных решений с первой сдачи.
- Пагинация: keyset по `(CreatedAt, Id)` был новым и потребовал объяснения; сдвиг страниц при `OFFSET` и вставке новой записи распознан после уточнения.
- Тест конкурентности: предложены сигнальный примитив для совместного старта запросов, условный `UPDATE` с проверкой остатка и проверка результата в реальной БД. Не названы сразу точный примитив и все утверждения о двух ответах; исполняемого теста нет.
- Безопасность: HMAC сначала смешан с сертификатом; схема общего секрета и проверки подписи разобрана. CSRF назван самостоятельно, но серверный antiforgery-токен потребовал объяснения; отдельно разобраны форма, cookie и проверка токенов. Stored XSS был перепутан с SQL injection и затем объяснён на выводе пользовательского HTML.
- gRPC: риск накопления записей при медленном клиенте и ограниченная очередь поняты; потоковая выдача и прокидывание cancellation token названы. Разница deadline и отмены объяснена с уточнением; для вложенного вызова B важно передавать исходный абсолютный deadline, а не новые три секунды.
- CI/CD: для одновременных деплоев предложена проверка версии, затем уточнена блокировка всего интервала проверки и применения. Расширение схемы для нового обязательного `Source` разобрано. При переименовании `Status → State` пользователь правильно описал переход с двумя колонками. Невалидное уточнение ассистента про работу исходных Pod после перехода на dual-write **не снижает оценку ответа**; ассистент признал ошибку.
- RabbitMQ: верно назван `fanout` для двух отдельных очередей. Накопление сообщений в заранее созданной очереди выключенного сервиса потребовало объяснения; отдельная отметка доставки в каждом сервисе для этого не нужна. `429` верно классифицирован как временная ошибка, `400` с неверным номером — как постоянная; риск немедленного повтора `429` понят.
- Feature flags: стабильная группа 5% клиентов через запись выбора в БД предложена самостоятельно. Стабильный хеш по `CustomerId` разобран как альтернативный способ.
- Kubernetes: `StatefulSet` выбран для PostgreSQL, но `PVC` не вспомнился. Самостоятельно указано, что три Pod не дают автоматическую репликацию PostgreSQL. При квоте `requests.cpu` правильно замечено превышение, но различие отказа при admission и `Pending` при нехватке узла потребовало объяснения. Для `Pending` названы события Pod.
